What this file does

There is no operating system on this board. When the chip is powered or reset, the boot loader in its internal read-only memory loads the firmware image from flash and jumps into it; the function in this file is where that jump ends up. Nothing has been configured at that point: the processor runs at its start-up clock speed, no pin has been assigned to a peripheral, the external memory is not reachable, and no radio is running.

This file performs five kinds of work, in a fixed order:

  1. Claim the hardware. A single call produces one value per peripheral, and those values are the only way to reach the hardware. Handing one away is what gives another part of the program the right to use that peripheral.
  2. Configure the parts that everything else depends on: the external memory, the processor and peripheral clocks, and the hardware timer that all delays and timeouts are measured against.
  3. Set up the connections to the outside world: the indicator light on GPIO21, and the two-wire I2C bus on GPIO5 and GPIO6 that both sensors are attached to.
  4. Reserve the measurement history in the external memory, so that the first reading a sensor produces already has somewhere to be stored.
  5. Start the six tasks that do the actual work, giving each of them the hardware it needs, and set up the Wi-Fi driver and network stack the last three of them run on.

What this file does not do

  • It does not talk to either sensor. It only checks which addresses answer on the bus, and prints them.
  • It does not read, store or serve measurements. The tasks do that.
  • It does not contain a loop. It runs once, from top to bottom, and finishes.
  • It does not join the Wi-Fi network. It creates the driver and the network stack; joining the network, obtaining an address and answering requests are the work of three separate tasks.
  • It does not decide when anything happens. Every interval in the firmware is defined in the task that uses it.

How the program is arranged

Tasks instead of threads

The firmware is built on a cooperative scheduler called an executor. A task is a function that runs until it needs to wait — for a timer to expire, for the I2C bus to become free, for a network packet to arrive — and at that point it returns control to the executor, which runs whichever other task is ready. There is no pre-emption: a task keeps the processor until it reaches a waiting point of its own.

This means the tasks never interrupt each other in the middle of an operation, and the whole program runs on a single processor core without needing one stack per task. It also means that a task that never waits would stop every other task; every task in this firmware waits on a timer or on the network.

Why the start-up function finishes

Starting a task registers it with the executor; it does not call it. When the body of the start-up function reaches its end, the six tasks it registered are still there and the executor keeps running them. The function does not return to a caller, because there is no caller: it is the outermost function of the program.

No heap

The firmware allocates nothing at run time in the usual sense. Anything that has to outlive the start-up function — the timer, the clock configuration, the I2C bus, the network stack and its buffers — is placed in a storage slot reserved at compile time and filled exactly once. Filling such a slot returns a reference that is valid for the rest of the program run, which is precisely what a task needs, because a task also lives for the rest of the program run.

The one exception is the measurement history, which is far too large for the internal memory. It is carved out of the 8 MB of external memory on the module by the bump allocator in src/utils/psram.rs. That allocator never frees anything either, so its results are equally permanent.

Hardware ownership

Each peripheral of the chip is represented by exactly one value. That value cannot be copied, so it can be in only one place at a time, and whoever holds it is the only part of the program that can use the corresponding hardware. This is how the firmware guarantees, without any run-time checking, that two parts of the program never configure the same pin or drive the same bus.

The one piece of hardware that is shared

Two sensors sit on the same I2C bus, so two tasks need the same peripheral. The bus is therefore placed behind a lock: a task takes the lock, performs a complete exchange with its sensor, and releases it. Because a task can only be interrupted at a point where it waits, and because the lock is held across the whole exchange, the bytes of one sensor's conversation can never be interleaved with the other's. Both sensor tasks receive the same reference to the same locked bus.

A task that waits while holding the lock blocks the other task for that long. Both sensor drivers avoid this: they release the lock before their long waits — the five-second conversion of the carbon dioxide sensor and the five-second interval of the particulate sensor — and take it again for the next exchange.

Why the order matters

Most of the sequence in this file could be rearranged without effect, but four ordering constraints are real and are the reason the file looks the way it does.

ConstraintReasonWhat would otherwise happen
External memory is mapped first, before the clocks are raised Mapping it retunes the timing of the memory interface and reconfigures the data cache Retuning the memory interface after other peripherals are running, or against a clock speed that is about to change, can leave the cache and the memory disagreeing
Clocks are configured before any peripheral is created Every peripheral derives its own timing from the clock configuration and is given a reference to it Peripherals set up against one clock speed would produce wrong bit rates and wrong delays once the speed changed
The timer is handed to the executor before anything waits All waiting in the firmware is expressed in terms of that timer The first attempt to wait would have no clock to wait on
The measurement history is reserved before the sensor tasks are started Readings taken while no history exists are discarded rather than queued The earliest readings would be lost, silently

The Wi-Fi driver is set up after the sensor tasks are started rather than before. Nothing forces that order, but it means the sensors begin measuring immediately instead of waiting for the radio to come up, and the first readings are already stored by the time a browser can ask for them.

What appears on the serial port

This file prints three things: a banner, the result of the bus scan, and one line about the measurement history. Everything printed after that comes from the tasks. 

XIAO ESP32-S3 Embassy firmware started; blinking GPIO21
Scanning I2C0 at 100 kHz (SDA GPIO5, SCL GPIO6)...
  [progress output from the scan]
I2C device found at 0x62
I2C device found at 0x69

The two counts are not written anywhere as numbers; they are worked out at compile time from the retention period and the two measurement intervals: 24 hours divided by 10 seconds is 8640 readings for the carbon dioxide sensor, and 24 hours divided by 5 seconds is 17280 for the particulate sensor. The two sizes in KiB are measured at run time as the difference in free external memory before and after the reservation, and are shown here as NNN rather than invented.

If a sensor is not connected, or is not powered, its address simply does not appear in the scan. The corresponding task is started anyway and reports its own failures; the scan is a diagnostic, not a gate.

Crate attributes lines 1–2

Compilation

no_std removes the part of the Rust standard library that assumes an operating system: files, threads, sockets, and everything that needs a heap. What remains is the core library — integers, slices, iterators, results — which needs nothing underneath it. This is a requirement, not a preference: there is no operating system here to provide the rest.

no_main removes the usual program entry point. On a desktop, the C runtime starts, prepares the arguments and the environment, and then calls main. Here the chip jumps straight into the firmware, so the entry point has to be produced by the chip support code instead; the attribute above the start-up function below does that.

Chip support

Everything that touches the chip's own hardware comes from one library:

  • ClockControl chooses the clock speeds; Clocks is the resulting configuration that peripherals are built against.
  • Delay is a busy-wait: it holds the processor for a given time without involving the executor. The bus recovery routine needs this, because it has to produce pulses of a few microseconds.
  • Io unlocks the pins; Output is a pin configured to drive a level; Level is that level; AnyPin hides which pin it is, so that the blink task does not have to name pin 21 in its own signature.
  • Peripherals is the collection of every peripheral value.
  • Rng is the hardware random number generator.
  • SystemControl gives access to the clock and reset control block.
  • TimerGroup is a pair of hardware timers. OneShotTimer and PeriodicTimer are the two ways a timer can be used: fire once at a given moment, or fire repeatedly. ErasedTimer hides which timer it is, so that timers from different groups have the same type and can be stored in one array.

Storage

Five things created inside the start-up function have to survive after it ends, because tasks keep using them. A value created on the stack of a function disappears when the function returns, and there is no heap to move it to, so each of them is given a slot here.

A slot is exactly the right size for its contents, is reserved by the compiler in the program image, and starts out empty. Filling it is allowed once; a second attempt stops the program rather than overwriting a value that other parts of the program are already using. In return, filling it produces a reference that is guaranteed to remain valid for as long as the program runs — which is what makes it safe to hand that reference to a task that also runs forever.

Entry point

The attribute generates the real entry point around this function: the symbol the boot loader jumps to, the code that prepares the processor and the memory before any Rust code runs, the creation of the executor, and the registration of this function as the executor's first task. The spawner parameter is supplied by that generated code.

External memory and clocks lines 46–52

    // Map the external PSRAM before anything else: the routine retunes the
    // memory-SPI timing and reconfigures the data cache, so it has to run
    // before the clocks are raised and before any other peripheral is set up.
    let mut psram = Psram::init(peripherals.PSRAM);
Hardware

The module on this board carries 8 MB of memory outside the chip, reached over a fast serial connection. It is not usable until it is mapped: the chip has to be told the connection's timing and which range of addresses corresponds to it, and the data cache has to be reconfigured so that reads and writes to that range go through the cache correctly.

That reconfiguration is why this is the very first step. It changes the timing of a memory interface and the behaviour of the cache, which are exactly the things every later step relies on. Doing it first means no other peripheral has been configured against settings that are about to change.

What comes back is not memory but an allocator over it: a marker that starts at the bottom of the mapped range and only moves upwards. It hands out permanent blocks and never takes any back, which is all this firmware needs, because the only thing it allocates is the measurement history and that lives for the whole program run. 

    let system = SystemControl::new(peripherals.SYSTEM);
    let clocks = CLOCKS.init(ClockControl::max(system.clock_control).freeze());
Hardware

After reset the chip runs slowly, on a conservative clock. The first line takes control of the block that distributes clocks to the processor and to the peripherals; the second raises them to the highest setting this chip supports and then freezes the configuration.

Freezing is what makes the configuration trustworthy. Once frozen it cannot be changed, so every peripheral created afterwards can be handed a reference to it and rely on the numbers in it staying true. A bus that computes its bit rate from a clock speed that later changed would silently run at the wrong speed.

The result is placed in its permanent slot immediately, because peripherals hold a reference to it and those peripherals are handed to tasks.

Time source lines 54–58

    // Drive `embassy_time` from TIMG0's first timer.
    let timg0 = TimerGroup::new(peripherals.TIMG0, clocks);

Time

Every wait in this firmware — a blink interval, a sensor's measurement period, the five seconds a conversion takes, a network timeout — is a request to be woken at a particular moment. Something has to measure those moments, and that something is one hardware timer.

The four lines are four separate steps:

  • Take the first of the chip's two timer groups, built against the frozen clock configuration so that its counting rate is known.
  • Take the first timer of that group and erase its identity, so that it has the same type as any other timer and can be stored in an array.
  • Wrap it as a one-shot timer — one that is armed for a single future moment and re-armed each time — and put the resulting array into its permanent slot.
  • Hand it to the chip support layer, which from now on answers the question "what time is it" and "wake this task at that time".

One timer is enough because the executor only ever needs to know when the earliest waiting task should wake. It arms the timer for that moment, and when the timer fires it re-arms it for the next one.

Nothing in the firmware may wait before this line. The second timer group is deliberately left alone here; the Wi-Fi driver claims it later for its own periodic tick.

Hardware

Two peripherals are needed to use a pin. One is the pin block itself, which drives and reads levels; the other is the switch matrix that decides which internal signal a physical pin is connected to. Taking both together produces a value from which individual pins can be taken.

Pin 21 is then configured as an output starting at the low level, and its identity is erased. The erasure is the interesting part: the blink task's signature says it accepts an output pin, not that it accepts pin 21. The board's wiring is stated here and only here, so a different board or a moved wire changes one line in one file and nothing in the task.

Whether "low" means the light is on or off depends on how the light is wired on the board. Either way the light alternates, which is all it is there for: a steady blink is visible evidence that the executor is still running tasks.

I2C bus lines 64–70

    let mut bus = I2cBus::new(

Hardware

Both sensors are on one two-wire bus: a data line on GPIO5 and a clock line on GPIO6. The bus controller and the two pins are handed over together, which is what makes them a bus rather than three separate pieces of hardware.

The clock configuration is needed because the bus speed of 100 kHz is produced by dividing a peripheral clock; without knowing that clock's rate the divisor cannot be computed.

The busy-wait is needed for a different reason. When a sensor stops responding in the middle of a transfer, the bus can be left with the data line held low, and no further transfer is possible until it is freed. Freeing it means driving the two pins by hand for a few microseconds at a time — too short to go through the executor, which measures waits in whole milliseconds and involves a scheduling round trip. The bus module therefore keeps a busy-wait for that purpose only.

The bus is not yet shared at this point. It is an ordinary local value, which is why the scan on the next lines can use it directly without taking any lock.

    let devices = bus.scan();

Diagnostics

The scan addresses every legal address on the bus in turn and records which ones answer. Two are expected: 0x62 for the carbon dioxide sensor and 0x69 for the particulate sensor. Anything else on the list is another device on the same wires; anything missing is a wiring, power or address problem.

The result is only printed. Nothing in the firmware acts on it: the sensor tasks are started regardless, and each of them reports its own failures if its sensor is absent. This is deliberate — a sensor that is plugged in after start-up will begin working on its own, without a restart.

A scan is unusually demanding on a bus, because most addresses do not answer and each silence has to be recovered from before the next address can be tried. The details, and the fault in the chip support code that makes the recovery necessary, are described in the documentation of src/drivers/i2c_bus.rs.

Storage

This reserves two ring buffers in the external memory, one per sensor, each large enough for a full day of readings. A ring buffer holds a fixed number of entries and, once full, overwrites the oldest; that is what keeps memory use constant no matter how long the board runs.

The two capacities are not chosen by hand. They are computed at compile time from the retention period and the interval each task uses: a day divided by ten seconds is 8640 carbon dioxide readings, a day divided by five seconds is 17280 particulate readings. Changing an interval in a task changes the capacity automatically, and the two can never fall out of step.

This is the only point in the whole function where it waits, because the shared storage is itself behind a lock and taking that lock is a waiting operation. Nothing else holds it at this moment, so the wait is not a real one.

The reservation reports either the number of bytes taken or nothing at all, and both outcomes are handled. The successful message repeats the capacities, the period in hours, the size taken and the size still free, so a single line of output confirms both that the memory is there and how much of it the firmware is using.

If the memory is absent or too small, the firmware does not stop. It prints one line and carries on with no history at all: readings are still measured and still shown as current values, but nothing is retained, and the web server reports an empty history. This is a deliberate choice — losing the graphs is much less serious than losing the sensor entirely.

Sharing the bus lines 95–97

    // Hand the bus to the sensor tasks; each one locks it for a whole
    // transaction, so their transfers can never interleave.
    let bus: &'static SharedI2cBus = BUS.init(Mutex::new(bus));
Sharing

Up to this line the bus was an ordinary local value used by one piece of code. This line changes that in two ways at once, and the order is significant.

First it is wrapped in a lock. A lock turns a value that only one holder may use into one that many may use, provided they take turns: a task asks for the contents, waits if another task has them, and gives them back when it is finished. Second, the locked bus is placed in its permanent slot, producing a reference valid for the rest of the program run. Both sensor tasks are given a copy of that reference, which is possible precisely because the lock is what enforces the taking of turns.

What the lock protects against is subtle. Every exchange with a sensor is several separate operations — send a command, wait, read the answer — and a reading is only correct if the answer read belongs to the command sent. If the other task were allowed to speak to its own sensor in between, both sensors would receive commands that were not meant for them. Holding the lock for the whole exchange, rather than for each individual transfer, is what prevents this.

The lock is of the kind that briefly disables interrupts while it changes hands, so it works no matter what the executor is doing at that moment. The cost is a very short interrupt-free window, which is acceptable because taking the lock is a short operation, unlike holding it.

Starting the sensor tasks lines 99–101

Tasks

Each of these registers a task with the executor. Note what is not happening: none of these functions runs here. Calling one produces a description of work to be done; the executor is what performs it, once this function reaches a waiting point or ends.

Each task is given exactly what it needs and nothing more. The blink task receives the output pin and moves it — after this line no other part of the program can touch pin 21. The two sensor tasks receive the same reference to the same locked bus, which is how two tasks can drive one piece of hardware.

The particulate sensor is started before the carbon dioxide sensor for a practical reason: it needs about thirty seconds of running before its readings settle, so the earlier it begins the better.

Registering a task can fail, and the result is discarded here rather than checked. The only way it can fail is an attempt to start the same task a second time while the first is still running, and each of these is started exactly once, so the case cannot arise. It is worth knowing that if it ever did, the task would simply not start and nothing would be printed.

Radio

The Wi-Fi driver cannot share the executor's timer. It maintains its own schedule of events measured in much smaller units — when to listen, when to transmit, when to acknowledge — and those deadlines are met by interrupts rather than by the executor. It is therefore given the second timer group, untouched until now for exactly this reason.

The random generator produces two 32-bit values, which are joined into one 64-bit number: the first is shifted into the upper half, the second occupies the lower half.

That number becomes the network stack's starting point for connection sequence numbers. Every TCP connection begins by choosing a number that both ends then count from. If a device chose the same starting number after every restart, a stray packet from an earlier connection could be mistaken for part of a new one, and an outsider who could guess the number could inject data into a connection without seeing it. Starting from an unpredictable value removes both problems.

The manufacturer's documentation states that this generator produces genuinely unpredictable values only while the radio is active. Both values here are read before the radio has been started, so the seed is less unpredictable than it looks. Reading it after the radio came up would be stronger.

Network

The stack is the layer between raw packets and connections. It assembles and takes apart the protocol headers, keeps track of open connections, retransmits what was not acknowledged, and answers the low-level requests other machines on the network make. Four things go into it:

  • The device — the packet-moving half created just above.
  • The address configuration — set to obtain an address automatically from the network's server, rather than using a fixed one written into the firmware. This is what allows the same image to be flashed onto any board and used on any network. The cost is that the address is not known in advance, which is why it is printed once it arrives.
  • The resources — the connection table and the send and receive buffers. The number of simultaneous connections is fixed at compile time, which is what makes the memory use of the network predictable; the value is defined in the web server file, next to the code that uses it.
  • The seed — the unpredictable starting point for connection sequence numbers.

The resources are placed in their own permanent slot inside the call that places the stack in its slot, so both exist for the rest of the program run. The stack is then referred to by two different tasks through the same reference.

The middle one is easy to overlook and is the one everything depends on. The stack does no work by itself; it is a collection of state that has to be driven. If that task were not started, the board would join the network and then answer nothing at all.

The closing brace is the end of the start-up work. The six tasks remain registered, and the executor runs whichever of them is ready — for the rest of the time the board is powered.

Failure behaviour

Failures during start-up fall into two groups: those the firmware carries on from, and those that stop it. The distinction is whether continuing would produce something useful.

SituationWhat happensEvidence
A sensor does not answer the scan Its address is missing from the list. Its task is started anyway and reports its own read failures. A sensor connected later starts working without a restart. The missing address in the scan output, followed by failure messages from that sensor's task
No device answers at all One line is printed saying so. Both tasks are still started; both then fail continuously. No I2C devices acknowledged on I2C0
External memory too small or absent The firmware continues with no history: current readings still work, nothing is retained, and the web server reports an empty history. History: PSRAM too small, readings will not be retained
Radio subsystem fails to start The firmware stops. Continuing would leave a board that measures but cannot be reached, which is harder to diagnose than a clear stop. Wi-Fi initialisation failed, with a backtrace
The station interface cannot be created The firmware stops, for the same reason. could not create the Wi-Fi station interface, with a backtrace
The network cannot be joined, or no address is issued Nothing here fails. The connection task keeps trying, the light keeps blinking and the sensors keep measuring. The board becomes reachable as soon as the network allows it. Messages from the connection task; no address line
A task cannot be registered The task does not start and nothing is printed. This can only happen if the same task is started twice, which this file never does. Silence — the task's own output is simply absent
Nothing at all is printed Execution did not reach the banner. That points at the three steps before it: mapping the external memory, configuring the clocks, or setting up the time source. An empty serial port after reset
