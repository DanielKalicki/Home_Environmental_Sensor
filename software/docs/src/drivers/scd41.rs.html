What this file does

The SCD41 is a sensor made by Sensirion that reports the carbon dioxide concentration of the air, together with the temperature and the relative humidity. It is connected to the two-wire I2C bus described in src/drivers/i2c_bus.rs and answers at address 0x62.

This file is the translation layer between that sensor and the rest of the firmware. It provides:

  1. The command codes. Every operation the sensor understands is a fixed 16-bit number taken from the datasheet. They are named constants here rather than numbers scattered through the code.
  2. The waiting times. The sensor does not answer instantly; each command has a published time it needs before it can be spoken to again. Those times are stored next to the commands.
  3. The checksum. Every pair of bytes the sensor sends is followed by a check byte. This file recomputes it and rejects any word that does not match, so corrupted readings are never published.
  4. Unit conversion. Temperature and humidity arrive as plain 16-bit numbers with no units. The formulas that turn them into degrees Celsius and percent live here.
  5. The settings read-outs. The sensor keeps several configuration values in its own memory — the temperature offset, the altitude, the assumed air pressure, and four values controlling its automatic self-calibration. This file can read all of them back and convert them into ordinary units, so the start-up log can state how the attached sensor is configured.

What this file does not do

  • It does not decide when to measure. The ten-second schedule lives in src/tasks/scd41_task.rs.
  • It does not obtain or release the shared bus. It is handed a ready-to-use I2C block and uses it.
  • It does not store readings or retry after a failure. It reports the failure and returns.
  • It does not implement the sensor's continuous measurement mode, its forced calibration command, or any command that changes a setting. The settings commands present here are read-only: every configuration value is reported, none is written. Only the on-demand flow the firmware actually uses is present.

Constraints that shaped the implementation

  • The bus is shared with a second sensor, so the driver is deliberately split: starting a measurement and collecting it are two separate calls, and the five seconds in between belong to nobody.
  • The firmware has no heap. The largest buffer here is nine bytes on the stack.
  • Floating-point arithmetic is used only in the two conversion functions, and only when a caller asks for a converted value. The stored reading remains an exact integer.

The sensor protocol, in the detail needed to read this file

Commands

Every operation is a 16-bit number sent as two bytes, most significant byte first. Reading a measurement, for example, is 0xEC05, which travels as the byte 0xEC followed by the byte 0x05. This ordering is called big-endian.

Execution time

After the command bytes have been delivered, the sensor is busy. The datasheet states how long for each command, ranging from one millisecond to five seconds. Speaking to the sensor before that time has elapsed produces no answer. There is no "ready" signal to poll; the waiting time is simply respected.

Answers: words with a check byte

Data always comes back in groups of three bytes: two data bytes, most significant first, followed by one check byte. The check byte is a CRC-8, a small number computed from the two data bytes using a fixed rule. The receiver repeats the computation; if the result differs from the byte that arrived, one of the three bytes was corrupted in transit and the whole group is discarded.

Every command that reports a setting — the sensor variant, the temperature offset, the altitude, the pressure and the four self-calibration values — answers with a single word in this shape. The check byte is computed the same way and covers the same two data bytes; only the number of groups differs.

Two separate exchanges, never one

Many I2C devices allow a command and its answer to be combined into a single exchange, with a repeated START in the middle instead of a STOP. The SCD41 does not permit this. The command must be delivered in one complete exchange, and the answer collected in a second one after the waiting time. This is why the code never uses the combined write-then-read call offered by the hardware driver.

Measurement flow

Module description lines 1–12

//! Minimal driver for the Sensirion SCD41 CO2 / temperature / humidity sensor.
//!
//! Only the single-shot ("on demand") measurement flow is implemented:
//!
//! 1. `measure_single_shot` (0x219D) triggers one conversion.
//! 2. The sensor needs 5000 ms to finish it.
//! 3. `read_measurement` (0xEC05) returns 3 words, each followed by a CRC-8.
//!
//! Every word on the wire is big-endian and protected by a CRC-8 with
//! polynomial 0x31, initial value 0xFF, no reflection and no final XOR.

#![allow(dead_code)]
Documentation and one attribute

The //! lines describe the file as a whole. They state the three steps of a measurement and the checksum settings, which is the minimum needed to compare this code against the datasheet.

"Single-shot" means the sensor measures once, when asked. The alternative offered by the sensor is a continuous mode in which it measures on its own schedule; that mode is not used, so it is not implemented.

#![allow(dead_code)] switches off the warning that reports items which are never used. Several commands here are complete and correct but not called by this firmware — reinit, wake_up, measure_single_shot and the humidity-and-temperature-only variant. They are kept because they are part of the sensor's documented behaviour and would otherwise have to be written again when needed. The attribute stops each of them producing a warning at every build.

The suppression applies to the whole file, so a genuinely unused item added later will also not be reported. This is the cost of keeping the unused commands.

Checksum settings lines 52–53

const CRC8_POLYNOMIAL: u8 = 0x31;
const CRC8_INIT: u8 = 0xFF;
Datasheet values

The two numbers that define the checksum used by every Sensirion sensor. The polynomial is the pattern combined into the running value; the initial value is where the computation starts.

Both must match the sensor exactly. A wrong value here would not cause an obvious failure — it would cause every reading to be rejected as corrupt, and the sensor would appear to be broken.

The same two numbers are used by the SPS30 driver in src/drivers/sps30.rs, which repeats the computation rather than sharing it, so that each driver can be read on its own.

The error type lines 55–68

/// Errors reported by the driver.
#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Error {
    /// The I2C transfer itself failed (no acknowledge, timeout, ...).
    Bus(I2cError),
    /// A word came back with a CRC that does not match its data bytes.
    Crc,
}

impl From<I2cError> for Error {
    fn from(error: I2cError) -> Self {
        Error::Bus(error)
    }
}
Data structure

Exactly two things can go wrong, and they call for different responses:

  • Bus — the exchange itself failed. Nothing answered, or the transfer was cut short. This usually means the sensor is absent, unpowered, or was left in a state where it ignores commands. The original hardware error is carried inside so it can be printed.
  • Crc — the exchange succeeded and the sensor answered, but the check byte did not match. The sensor is present and talking; the wires are picking up interference or the connection is marginal.

The four derived properties: Debug allows the error to be printed; Clone and Copy make it a plain value that can be passed around freely; PartialEq allows two errors to be compared.

The From block states how a hardware error becomes one of these. Once that conversion exists, the question-mark operator used throughout the file performs it automatically, which is why lines such as self.i2c.write(...)? need no explicit conversion step.

The sensor type lines 70–95

/// Sensor type reported by `get_sensor_variant` (0x202F).

/// The variant is encoded in bits 15..12 of the returned word.

    Scd40,
    /// Bits 15..12 == 0b0001.

    /// Bits 15..12 == 0b0101.
    Scd43,
    /// Any other encoding, carrying the raw 4-bit field.
    Unknown(u8),

External interface · printed by the task at start-up

The SCD40, SCD41 and SCD43 are three members of one family. They share the same address, the same commands and the same wiring, and cannot be told apart by looking at the bus. They differ in what they promise: the SCD41 supports the on-demand measurement this firmware depends on and specifies its carbon dioxide reading over a wider range than the SCD40.

Naming the four possibilities, rather than passing the raw number around, means the start-up line reads variant: Scd41 and a comparison against the expected type is one equality test.

Unknown(u8) keeps the four bits that were actually received. A future part in the same family, or a bus fault that corrupts the value in a way the check byte happens not to catch, is therefore reported with the number responsible instead of being silently reduced to "not an SCD41".

impl SensorVariant {
    /// Decode the raw word returned by `get_sensor_variant`.
    fn from_raw(raw: u16) -> Self {
        match (raw >> 12) as u8 & 0x0F {
            0b0000 => SensorVariant::Scd40,
            0b0001 => SensorVariant::Scd41,
            0b0101 => SensorVariant::Scd43,
            other => SensorVariant::Unknown(other),
        }
    }
}
Datasheet values

Turns the one word the sensor sends into one of the four names.

raw >> 12 moves the top four bits down to the bottom, discarding the twelve reserved bits below them. & 0x0F then keeps only those four bits. The two steps together extract the type number and nothing else, so reserved bits that a future sensor may use cannot affect the result.

The three known patterns are written in binary rather than as decimal numbers, because that is the form the datasheet uses; comparing the code against it requires no arithmetic.

The final arm catches everything else and keeps the value. A match in Rust must cover every possibility, so a fourth pattern appearing on the wire cannot fall through unhandled.

The function is private: it is meaningful only for a word produced by 0x202F, so only the read-out that sends that command can call it.

External interface · stored in the history

One reading: six bytes, three 16-bit numbers, exactly as they arrived from the sensor. This is the value the task hands to shared_state.rs, and the value the history keeps.

Carbon dioxide is already in parts per million and is stored as such. Temperature and humidity are stored raw and are converted only on demand, for three reasons: the raw form is exact, it occupies half the space of a floating-point number, and it avoids performing arithmetic on readings that may never be looked at.

Eq is among the derived properties, which is only possible because every field is an integer. It states that two readings can be compared for exact equality — a claim that cannot be made about floating-point numbers, and therefore could not be derived if the conversions were applied here.

Storing six bytes rather than the twelve a converted form would need is what allows the history in external memory to hold 8640 readings per sensor.

impl Measurement {
    /// Temperature in degrees Celsius: `-45 + 175 * raw / 2^16`.
    pub fn temperature_celsius(&self) -> f32 {
        -45.0 + 175.0 * (self.temperature_raw as f32) / 65535.0
    }

    /// Relative humidity in percent: `100 * raw / 2^16`.
    pub fn humidity_percent(&self) -> f32 {
        100.0 * (self.humidity_raw as f32) / 65535.0
    }
}
Called by the task and by the web server

The two formulas from the datasheet, applied to the raw words.

Temperature spans a fixed range: raw 0 means −45 °C, the largest possible raw value means +130 °C, and everything in between is spread evenly. A raw word of about 24000 corresponds to roughly 19 °C.

Humidity spans 0 % to 100 % over the same word.

The divisor is 65535, which is the largest value a 16-bit word can hold. The doc comments write this as 2^16; the exact value used in the code is 2^16 − 1, which is the divisor the datasheet specifies. The difference between the two is smaller than the sensor's accuracy, but the code is the correct form.

Both take the reading by reference and return a new number without changing anything, so calling them twice is free of consequence.

The checksum computation lines 121–137

/// Compute the Sensirion CRC-8 over a data word.
fn crc8(data: &[u8]) -> u8 {
    let mut crc = CRC8_INIT;

    for byte in data {
        crc ^= byte;
        for _ in 0..8 {
            if crc & 0x80 != 0 {
                crc = (crc << 1) ^ CRC8_POLYNOMIAL;
            } else {
                crc <<= 1;
            }
        }
    }

    crc
}
Verification

Produces the check byte for a group of data bytes. In this file it is always called with the two bytes of one word.

Step by step. The value starts at 0xFF. For each data byte, that byte is combined into the value with an exclusive-or — an operation that flips exactly the bits the byte has set. Then the value is processed one bit at a time, eight times:

  • crc & 0x80 != 0 tests whether the highest bit is set.
  • If it is, the value is shifted one place to the left and the polynomial is combined into it.
  • If it is not, the value is only shifted.

Whatever remains after both bytes have been processed is the check byte. Nothing is applied afterwards, which is the "no final XOR" mentioned in the file description.

This procedure has a useful property: a change to any single bit of the data, and most changes to several bits, produce a different check byte. That is what makes a corrupted reading detectable.

The two shifts deliberately discard the bit that moves off the top. The result stays within one byte, which is what makes it an 8-bit checksum.

This is computed bit by bit rather than with a lookup table. A table would be faster but would occupy 256 bytes of memory permanently, and the computation runs six times per reading, once every ten seconds.

The driver value lines 139–146

/// SCD41 attached to an esp-hal I2C bus.
///
/// The I2C transfers themselves are blocking, but every datasheet-mandated
/// execution delay yields to the Embassy executor instead of busy-waiting.

    i2c: &'a mut I2C<'d, T, Blocking>,
    address: u8,
}
Data structure

The driver holds only two things: a borrowed I2C block and the address to speak to. It stores no state about the sensor, which means creating one costs nothing and there is no possibility of the driver's idea of the sensor drifting away from reality.

This is why the task creates a fresh Scd41 for every exchange rather than keeping one. The task does hold one piece of state itself — whether the sensor still needs initialising — but that belongs to the schedule, not to the protocol.

The comment describes the timing behaviour precisely. Sending the bytes occupies the processor until the transfer finishes, which at 100 kHz is a few hundred microseconds. Waiting out the execution time does not: the task is suspended and other tasks run, which is what allows a five-second conversion to cost nothing.

'a and 'd record how long the borrowed block lives, so the driver cannot outlive the block it borrows. T stands for whichever I2C hardware block is in use, so this driver is not tied to I2C0.

    async fn send_command(&mut self, command: u16, execution_delay_ms: u64) -> Result<(), Error> {
        self.i2c.write(self.address, &command.to_be_bytes())?;
        Timer::after_millis(execution_delay_ms).await;
        Ok(())
    }
Internal building block

Every command in this file that carries no data goes through these three lines.

to_be_bytes splits the 16-bit command into its two bytes, most significant first. 0xEC05 becomes the pair [0xEC, 0x05]. The name states the byte order explicitly, so it cannot be confused with the opposite convention.

The question mark at the end of the write is the early-return operator: if the exchange failed, the function stops immediately and hands the failure back to the caller, converted into Error::Bus by the conversion defined earlier. The wait is then not performed, which is correct — a command that was never delivered is not being executed.

Timer::after_millis(...).await suspends the calling task for the sensor's execution time. Other tasks run during it. This is the single most important difference between this driver and a busy-waiting one: the five-second conversion does not stop the rest of the firmware.

The function is private. Callers ask for operations by name; the command code and its execution time are supplied here, together, so the two can never be mismatched.

Internal building block

The single-word counterpart of read_three_words. Every settings read-out in this file goes through it: the sensor variant, the temperature offset, the altitude, the pressure and the four self-calibration values — eight callers, one exchange each, differing only in the command code they pass in.

The steps are the same as for three words, with the counts reduced to one: send the command and wait its execution time, read exactly three bytes, recompute the check byte from the first two, compare it with the third, and combine the two data bytes into a 16-bit number, most significant byte first.

The verification is not optional here either. A mismatch returns Error::Crc and no value at all. A settings word that arrived corrupted would otherwise be printed as fact at start-up, which is exactly the kind of quiet wrong answer the check byte exists to prevent.

The comment repeats the protocol requirement recorded on the three-word function, because this function is read on its own as often as that one: the command and its answer must be two separate exchanges, never a combined write-then-read.

Returning a plain number rather than an interpreted value is deliberate. What the word means — metres, hectopascals, hours, a yes-or-no answer, a type number in the top four bits — is decided by the read-out that called it, each of which applies its own conversion.

Verification

Turns the nine bytes into three verified words.

chunks_exact(3) walks the buffer in groups of three bytes, producing exactly three groups. zip pairs each group with the word it will fill, so the two advance together and no index arithmetic is written by hand.

For each group the check byte is recomputed from the first two bytes and compared with the third. A mismatch ends the function immediately with Error::Crc. Nothing partial is returned: if the third word is corrupt, the first two are discarded as well, because a reading is only meaningful complete.

u16::from_be_bytes combines the two verified bytes into one number, the first byte contributing the high half. This is the exact inverse of the to_be_bytes used when sending.

The function returns three plain numbers. What they mean is decided by the caller: the same three words are a serial number for one command and a reading for another.

Called by the task at start-up

Reads the identifier written into the sensor at manufacture. It is unique to that individual part.

The three words are joined into a single 48-bit number: the first is moved up 32 places, the second up 16, the third left where it is, and the three are combined. The result is placed in a 64-bit number because no smaller size can hold 48 bits; the top 16 bits are always zero.

The value itself is not used for anything. Its purpose is stated in the comment: it is a presence check. The task prints it and continues.

This is why the console line SCD41 ready, serial number: 0x... is a meaningful confirmation and not decoration: it cannot be printed unless a full exchange succeeded.

    /// applied to the reported temperature and humidity, not to CO2.

            .await?;
        Ok(175.0 * (raw as f32) / 65535.0)
    }
Called by the task at start-up

Reports how much the sensor subtracts from its own temperature reading before reporting it.

Why an offset exists at all. The sensor sits on a board that produces heat: the processor, the radio and the sensor's own gas measurement all warm the air immediately around it, so the temperature it measures is higher than the room's. The offset is the correction for that self-heating, and it depends on the board, not on the sensor. The factory value is 4 °C.

The conversion is the temperature formula without the shift. A temperature reading uses -45 + 175 × raw / 65535; an offset is a difference between two temperatures, so the −45 does not apply and only the scale factor remains. Writing the shift in here would report a 4 °C offset as −41 °C.

The second sentence of the comment is the one that matters when reading the data. The offset changes the temperature and humidity the sensor reports; it does not change the carbon dioxide value. A wrong offset therefore produces temperatures that are consistently too high or too low while the carbon dioxide readings remain correct.

Pressure and altitude are two ways of stating the same correction. Setting a pressure takes precedence over the stored altitude, because a measured pressure is more accurate than one estimated from height. This firmware sets neither, so the sensor uses whatever it holds.

The multiplication is why the result is a 32-bit number. The sensor's own unit is the hectopascal, one hundred pascals. Multiplying first would overflow and produce a small wrong number instead of a large correct one.

Pascals were chosen over hectopascals for the returned value because it is the unit that needs no further explanation at the point it is printed.

Reports whether the sensor corrects its own drift over time. It is enabled at the factory.

What automatic self-calibration does. The sensor remembers the lowest carbon dioxide concentration it has seen over a long period and assumes that this minimum was fresh outdoor air. It then adjusts itself so that this minimum reads as the target value. The assumption holds for a room that is aired regularly and fails for one that never is; in a permanently occupied space with no ventilation, self-calibration will gradually shift every reading downwards.

Knowing whether it is on is therefore necessary to interpret a long series of readings, which is why the value is printed at start-up.

raw != 0 converts the word into a yes-or-no answer. The datasheet defines only 1 and 0, and treating anything non-zero as enabled matches how the sensor itself behaves.
