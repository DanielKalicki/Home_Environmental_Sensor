What this file does

Every sensor on this board is wired to the same pair of signal wires, GPIO5 and GPIO6. There are nine of them, and only one may be spoken to at a time. This file owns those two wires and the hardware block that drives them, and provides three services:

  1. Exclusive access. It packages the hardware in a lock, so a sensor task can claim the wires for the whole of one exchange and no second task can interrupt it half way through.
  2. Recovery. Before every exchange it forces the two wires back to their idle state by driving them by hand, so an exchange that was abandoned earlier cannot leave the wires stuck.
  3. Discovery. At start-up it tries every valid device address in turn and prints which ones answered, which confirms the wiring without a logic analyser.

What this file does not do

  • It does not know any sensor command. The byte sequences for each device live in that device's own file under src/drivers/.
  • It does not decide when a measurement is taken. That timing lives in src/tasks/.
  • It does not store readings. Storage lives in src/utils/shared_state.rs.

Constraints that shaped the implementation

  • The firmware has no heap, so every buffer in this file is a fixed-size array whose size is fixed when the program is compiled.
  • The pin numbers are part of the type of the pins, so they cannot be chosen while the program runs. They are constants at the top of the file.
  • The hardware block cannot reconfigure the pins while it owns them, so recovery is only possible in the gaps between exchanges, when the block has been taken apart.

How I2C works, in the detail needed to read this file

I2C is a two-wire connection shared by one controller (here, the microcontroller) and any number of peripheral devices (here, the nine sensors listed below).

WireNamePurposeOn this board
SDASerial dataCarries the bits, one at a time, in either direction.GPIO5
SCLSerial clockDriven by the controller; each pulse transfers one bit.GPIO6

Neither wire is ever driven high by a device. Every device can only pull a wire down to 0 V or let go of it; a resistor on the board pulls the wire back up to the supply voltage when nobody is holding it down. This arrangement is called open drain, and it is why two devices can share a wire without damaging each other, and also why a device that is holding a wire down blocks everybody else.

An exchange has a fixed shape:

  • START — SDA goes from high to low while SCL is high. This tells every device that an exchange is beginning.
  • Address byte — seven address bits and one bit stating whether the controller intends to write or to read.
  • Acknowledge — the device with that address pulls SDA low for one clock pulse. This is the ACK. If no device holds that address, SDA stays high, which is a NACK: nothing answered.
  • Data bytes, each also acknowledged.
  • STOP — SDA goes from low to high while SCL is high. This releases the wires and returns them to idle, which is both wires high.
An address-only write — a START, an address byte, then a STOP with no data — is a complete, legal exchange that changes nothing inside the device. The scan in this file uses exactly that, which is why scanning cannot alter a sensor's settings.

The specific fault this file exists to work around

The hardware driver used here, esp-hal, abandons an exchange the moment it sees a NACK. It resets its internal state machine, but it does not emit the closing STOP condition. From the point of view of the wires, the exchange never ended.

The consequences build up:

  • A device that was part-way through sending a byte is still holding SDA low, waiting for clock pulses that never arrive.
  • Because SDA is held low, the next START cannot be produced — a START requires SDA to fall from high, and it is already low.
  • Every following exchange therefore fails as well, including exchanges with a sensor that is present and working.

During an address scan this is unavoidable: most of the 117 addresses have no device behind them, so most probes end in a NACK. Without a fix, a scan reports a device at the first address only, or nothing at all.

The fix is recover_i2c_bus, described in full further down. It takes the pins away from the hardware block, drives them by hand to produce nine clock pulses and one STOP, and hands them back. Nine pulses is the worst case: a device can be at most eight bits plus one acknowledge bit into a byte, so nine pulses always let it finish and release SDA.

//!
//! The SDA/SCL pins are fixed at compile time so that the bus-recovery routine
//! can take the concrete `GpioPin` types it needs to reconfigure them as
//! open-drain outputs.
//!
//! [`I2cBus`] owns the I2C0 peripheral together with both pins, so that a task

Documentation

Lines beginning //! describe the file as a whole rather than any single item below them. They are ignored when the program runs.

"Bit-banged" means the signal is produced by setting and clearing a pin in software, one edge at a time, instead of by a hardware block. It is slower and occupies the processor, but it is the only way to drive the wires when the hardware block has been taken apart.

"Fixed at compile time" refers to the pin numbers being part of the pin types. The recovery routine has to name those exact types in its signature, so the numbers cannot be selected while the program runs.

"Mutex" is a lock that only one holder may possess at a time. It is described in detail at the SharedI2cBus section below.

External interface · board wiring

The two constants record the physical wiring: the data wire is on GPIO5, the clock wire on GPIO6. They are public so that main.rs can print them in the start-up message rather than repeating the numbers in a second place.

The two type aliases attach those numbers to the pin types. GpioPin<5> and GpioPin<6> are different types, not one type holding a number, so handing the wrong pin to a function in this file is rejected when the program is compiled rather than producing a silent wiring fault at run time.

Changing the wiring means changing these two constants and re-flashing. The pin numbers cannot be supplied while the program runs, because a type cannot be chosen at run time.

A full scan therefore costs at most 117 addresses × 3 attempts, each preceded by a recovery sequence, plus a 10 ms pause between attempts. It runs once, at start-up, before any task is started.

The bus value and its shared form lines 44–61

/// Everything needed to drive I2C0, owned in one place.
///
/// The peripheral is deliberately *not* kept alive between transactions: a NACK
/// leaves the bus held, so it has to be bit-banged back to idle and rebuilt,
/// which is only possible while the pins are not owned by the peripheral.
pub struct I2cBus {
    i2c0: I2C0,
    sda: SdaPin,
    scl: SclPin,
    clocks: &'static Clocks<'static>,
    delay: Delay,
}
Data structure

One value holding the five things needed to run the bus: the hardware block, the two pins, the clock settings and the busy-wait timer. Keeping them together is what makes the alternation between hand-driven recovery and hardware-driven transfers possible, because both halves need the same two pins.

The important design decision is stated in the comment. The natural approach — build the I2C driver once at start-up and keep it — cannot work here. While the driver exists it owns the pins, and while it owns the pins they cannot be reconfigured as plain outputs, so the recovery sequence cannot be produced. The driver is therefore built and discarded around every single exchange.

&'static Clocks is a reference to something that exists for the whole run of the program. main.rs arranges this by placing the clock settings in permanent storage. Without it the bus value could not be stored permanently either.

/// The single I2C bus, shared by every sensor task.

/// A task holds the lock for a whole transaction, including the awaited
/// datasheet delays, so transfers from different sensors can never interleave.
pub type SharedI2cBus = Mutex<CriticalSectionRawMutex, I2cBus>;
External interface · to the sensor tasks

A short name for "an I2cBus behind a lock". This is the form all nine sensor tasks receive.

Mutex is short for mutual exclusion. The value inside cannot be reached at all except by calling lock(). If another task already holds the lock, the caller is suspended until the holder releases it; it does not spin or waste processor time. Because the value is unreachable without the lock, it is impossible to forget to take it.

CriticalSectionRawMutex selects how the lock protects its own internal state. This variant briefly disables interrupts, which makes it safe even if an interrupt handler were to touch the bus. It is the conservative choice and costs a few microseconds per lock.

Duration of the lock. A task takes the lock, performs one exchange, and releases it. The multi-second waits while a sensor produces a measurement happen with the lock released — see the sequence diagram above. The comment describes the guarantee this provides: an exchange is never cut in half by another task, no matter which of the nine is holding the lock.

Called by both sensor tasks

This is the routine every sensor exchange begins with. It does two things in order:

  1. Runs the recovery sequence, so the wires are known to be idle whatever happened previously.
  2. Builds a fresh I2C driver at 100 kHz on those pins and returns it.

The returned driver borrows the pins rather than taking them. When the caller finishes with it and it goes out of scope, the borrow ends and the pins become available for the next recovery. This is what makes the build-and-discard cycle described earlier possible without any manual clean-up step.

I2C_FREQUENCY_KHZ.kHz() converts the plain number 100 into a frequency value. The unit is attached in the type, so a value in kilohertz cannot be passed where megahertz is expected.

Recovery costs roughly 100 microseconds and runs before every exchange, including the ones that would have succeeded anyway. At measurement intervals of five and ten seconds this is not measurable, and it removes an entire class of intermittent fault.

Data structure

A list of addresses without a heap. The array always has room for 117 entries, and count records how many of those entries were actually filled. On a healthy board count is 2 and the remaining 115 entries are left at zero.

Both fields are private, so the only way to read the result is addresses(), which returns a view of exactly the filled part. A caller therefore cannot accidentally read the unused zeros and report a device at address 0x00.

The value occupies 117 bytes plus a length and is created on the caller's stack. It exists only during start-up and is discarded once printed.

Serial output

Draws one frame of the progress display. It is called once per address, so the line is redrawn 118 times during a scan.

A 30-character array is filled with full stops, then the leading portion is overwritten with hashes. The number of hashes is completed × 30 ÷ 117, using whole-number division, so the bar advances by one character roughly every four addresses and reaches 30 only on the final call.

\r at the start of the text is a carriage return: it moves the cursor back to the start of the current line without moving down. Combined with print!, which adds no line break, each frame overwrites the previous one, so a scrolling wall of 118 lines is avoided.

from_utf8 converts the array of bytes into text. It can fail in general, but here the array only ever contains full stops and hashes, so it cannot fail. The fallback text of thirty question marks exists solely to satisfy the requirement that every outcome be handled; it cannot be printed.

0x{:02X} prints the address in hexadecimal, in upper case, padded to two digits, which is the notation sensor datasheets use.

Bus recovery lines 134–163

/// Return the bus to a known idle state.
///
/// `esp-hal` aborts a transfer as soon as a NACK is seen and resets the I2C
/// state machine *without* emitting a STOP condition, so every non-answering
/// address leaves SCL/SDA in an undefined state. Those aborts accumulate over a
/// long scan until the bus is effectively locked and even a device that is
/// present stops answering. Clocking SCL nine times (so any slave that is
/// holding SDA can finish its byte) followed by a manual STOP releases it.
///
/// The pulses are microseconds wide, so this deliberately busy-waits with a
/// blocking `Delay` instead of yielding to the Embassy executor.
Documentation

This comment records the reason the routine exists. The behaviour it describes is a property of the chip support package, not of the sensors, and the full explanation is given in the section The specific fault this file exists to work around above.

The final paragraph explains the choice of timer. Everything else in this firmware is asynchronous: a task that waits hands the processor to another task. Here the waits are five microseconds long, which is far shorter than the cost of suspending and resuming a task, so an ordinary busy-wait is both simpler and faster. The whole routine occupies the processor for about 100 microseconds.

pub fn recover_i2c_bus(sda: &mut SdaPin, scl: &mut SclPin, delay: &Delay) {
    let mut sda = OutputOpenDrain::new(sda, Level::High, Pull::Up);
    let mut scl = OutputOpenDrain::new(scl, Level::High, Pull::Up);

Reconfigures both pins as software-controlled outputs for the duration of this function.

OutputOpenDrain is the mode required by I2C and described in the primer: the pin can pull the wire low or release it, but never drives it high. Any other output mode would fight the sensors for control of the wire.

Level::High makes both pins start released, so reconfiguring the pins does not itself disturb a bus that was already idle.

Pull::Up enables the chip's internal pull-up resistor, so the wire still returns to the high state even on a board without external pull-up resistors.

The new names sda and scl deliberately hide the parameters of the same name. The parameters cannot be used again inside this function, which prevents any attempt to drive a pin through two different configurations at once.

    for _ in 0..9 {
        scl.set_low();
        delay.delay_micros(I2C_RECOVERY_HALF_PERIOD_US);
        scl.set_high();
        delay.delay_micros(I2C_RECOVERY_HALF_PERIOD_US);
    }

Nine clock pulses, each five microseconds low and five microseconds high, giving 100 kHz.

Why nine. A device that was interrupted while sending can be at most eight data bits plus one acknowledge bit away from finishing. Nine pulses therefore always carry it past the end of the byte, at which point it stops holding SDA down and the wire becomes usable again.

SDA is not touched during this loop. It is left released, so whatever a device is doing with it can be observed by the device itself; the controller is only supplying the clock the device is waiting for.

The loop variable is written _ because the pulse number is not used. The name states that the value is deliberately discarded.

    // STOP condition: SDA goes low->high while SCL is high.
    sda.set_low();
    delay.delay_micros(I2C_RECOVERY_HALF_PERIOD_US);
    scl.set_high();
    delay.delay_micros(I2C_RECOVERY_HALF_PERIOD_US);
    sda.set_high();
    delay.delay_micros(I2C_RECOVERY_HALF_PERIOD_US);
}

Produces one STOP condition by hand, which is the signal that formally ends any exchange still thought to be in progress and returns the bus to idle.

The order is fixed by the I2C standard and each step matters:

  • SDA is pulled low, so that there is a low-to-high edge available to produce.
  • SCL is set high. It is already high after the last pulse of the loop; this makes the requirement explicit and independent of the loop.
  • SDA is released and rises. Because SCL is high at that moment, every device on the bus interprets this edge as STOP.

The five-microsecond pauses between the steps hold each level long enough for the devices to register it, and give the wire time to rise through the pull-up resistor.

When the function ends, the two OutputOpenDrain values are discarded and the pins are released, leaving them free for the I2C block to claim. Both wires are high, which is the idle state.

Takes the parts of the bus by reference rather than by ownership, so the caller keeps them and can continue using the bus after the scan.

The two guarantees in the comment are the ones a reader needs. No device is modified, because an address-only write carries no data, so the scan is safe to run on any bus. Each probe is independent, because the bus is returned to idle beforehand.

The result starts as 117 zeros with a count of zero, meaning "nothing found yet". This is the only storage the function uses.

Walks every address from 0x03 to 0x77. The ..= notation includes the last value, so 0x77 is probed rather than skipped.

completed converts the address into a count of finished probes: at address 0x03 nothing is finished, at 0x77 all but one are. That count drives the progress bar.

acknowledged records the outcome for this one address, and is reset for each address.

            recover_i2c_bus(sda, scl, delay);

Up to three attempts at one address. Each attempt repeats the full cycle: recover the wires, build an I2C block, probe, discard the block.

i2c.write(address, &[]) is the probe. The empty pair of brackets is a list of zero data bytes, so the exchange consists of a START, the address, and a STOP. Its result is success if some device acknowledged the address and failure if none did.

The extra pair of braces around these lines is deliberate. They end the life of i2c at the closing brace, which releases the pins immediately, before the next attempt's recovery needs them. Without them the block would stay alive until the end of the loop body and the recovery at the top of the next attempt would be rejected when the program is compiled.

Retrying is worthwhile because a sensor that is still powering up may miss the first probe; the SPS30 in particular takes time to become responsive after power is applied.

A successful probe stops the retries immediately, so a present device costs one attempt rather than three.

The 10 ms pause is skipped after the final attempt, since nothing follows it. Only the two gaps between the three attempts are paid for, which keeps the worst case for an empty address at roughly 20 ms.

When an address answered, it is appended to the array and the count is increased. The array holds 117 entries and there are only 117 addresses, so the write can never run past the end.

Three closing steps.

The final recovery leaves the bus idle for whoever uses it next. The last probe in the loop was almost certainly a NACK at 0x77, which would otherwise leave the wires in the abandoned state described earlier, and the first sensor exchange after start-up would fail.

The progress bar is redrawn once more with the completed count set to 117, which is the only call that produces a full bar of thirty hashes. Inside the loop the count is always at least one short.

println!() with nothing in it emits a line break, ending the line that the progress bar has been overwriting so that later output starts on a fresh line.

/// Print the outcome of [`scan_i2c`] to the serial monitor.
pub fn print_scan_result(result: &I2cScanResult) {
    if result.addresses().is_empty() {
        println!("No I2C devices acknowledged on I2C0");
    } else {
        for address in result.addresses() {
            println!("I2C device found at 0x{:02X}", address);
        }
    }
}
Called by main.rs

Turns the scan result into serial output. Reporting is kept separate from scanning so the scan can be run without producing output.

An empty result gets one explicit line rather than silence, which distinguishes "the scan ran and found nothing" from "the scan did not run".

Otherwise one line per address is printed, in ascending order, because the scan appends them in the order it probes.

This is the check to perform first when a sensor stops reporting: if its address is missing here, the fault is electrical — supply, wiring or pull-up resistors — and not in the sensor driver.

Failure behaviour

SituationWhat happensEffect on the rest of the firmware
An address does not answer during the scan Probed three times with 10 ms pauses, then treated as empty. None. This is the expected outcome for 115 of the 117 addresses.
No device answers at all No I2C devices acknowledged on I2C0 is printed. Start-up continues. The sensor tasks are started anyway and report their own errors as they fail to communicate.
A device is holding SDA low after an abandoned exchange The next call to acquire clocks it out and issues a STOP. Recovered automatically, without a reset and without any error being reported.
A sensor exchange fails part-way through This file takes no action; the failure is returned to the calling task. The task prints the error, waits, and repeats. Its next acquire begins with a recovery, so the failure does not carry over.
SDA is permanently held low, for example by a short circuit Recovery still runs and still completes; the STOP simply has no effect. Every exchange fails and every scan reports nothing. No part of the firmware hangs, because recovery has a fixed number of steps and cannot wait for the wire to rise.
Both sensor tasks want the bus at the same instant One takes the lock; the other is suspended until it is released. None beyond a short delay. The waiting task uses no processor time while suspended.
There is no situation in which this file waits indefinitely. Recovery is a fixed sequence of delays, the scan is a fixed number of probes, and the only unbounded wait — for the lock — is bounded in practice by the single short exchange the other task performs while holding it.
