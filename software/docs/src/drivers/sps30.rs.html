What this file does

The SPS30 is a sensor made by Sensirion that counts and sizes the dust particles in the air. It contains a small fan that draws air past a laser; particles crossing the beam scatter light, and the sensor works out from those flashes how many particles there are and how large they are. It is connected to the two-wire I2C bus described in src/drivers/i2c_bus.rs and answers at address 0x69.

This file is the translation layer between that sensor and the rest of the firmware. It provides:

  1. The command codes for starting and stopping the fan, asking whether a result is ready, and collecting one.
  2. The waiting times each command requires before the sensor can be spoken to again.
  3. The checksum, recomputed for every two bytes received, so a corrupted reading is rejected rather than published.
  4. Decoding. The sensor returns sixty bytes that have to be stripped of their check bytes and then reassembled into ten decimal numbers.

How this differs from the carbon dioxide sensor driver

The two drivers look similar and share the same checksum, but the sensors work in opposite ways. The SCD41 is asked for one measurement at a time and takes five seconds over it. The SPS30 runs continuously once started: its fan turns without interruption and a new result appears about once a second, whether or not anyone collects it. The firmware therefore starts it once and afterwards only asks "is there something new, and what is it".

What this file does not do

  • It does not decide when to read. The five-second schedule and the readiness polling live in src/tasks/sps30_task.rs.
  • It does not obtain or release the shared bus. It is handed a ready-to-use I2C block and uses it.
  • It does not retry. A failure is reported and returned.
  • It does not schedule fan cleaning, and it does not use the sensor's sleep mode, although both commands are implemented.

What the sensor measures

A reading contains ten numbers. They fall into three groups, and the difference between the first two groups is the single most important thing to understand about this sensor.

Mass concentration — four numbers, in micrograms per cubic metre

How much the particles in a cubic metre of air weigh. This is the quantity air quality limits are written in, and the one shown on the web page.

NameFieldIncludes particles up to
PM1.0pm1_01.0 micrometres across
PM2.5pm2_52.5 micrometres across
PM4.0pm4_04.0 micrometres across
PM10pm1010 micrometres across
These four are cumulative, not separate size bands. Every particle counted in PM1.0 is also counted in PM2.5, PM4.0 and PM10, so the four values never decrease as the size limit rises. PM2.5 is always at least PM1.0.

Number concentration — five numbers, in particles per cubic centimetre

How many particles there are, regardless of their weight. The same cumulative rule applies, and the series starts at a smaller size, 0.5 micrometres. These five are stored but are not shown on the web page, to keep the replies small.

The two groups can move independently. A large number of very small particles weighs almost nothing, so the count can rise sharply while the mass barely changes.

Typical particle size — one number, in micrometres

The average size of the particles currently being seen. It rises when the air contains coarse dust and falls when it contains fine smoke.

A micrometre, for scale

One micrometre is a thousandth of a millimetre. A human hair is roughly 70 micrometres across, so PM10 particles are about a seventh of the width of a hair and PM1.0 particles are about a seventieth.

The sensor protocol, in the detail needed to read this file

Commands, words and check bytes

Every operation is a 16-bit number sent as two bytes, most significant first. Data returns in groups of three bytes: two data bytes followed by one check byte, computed from those two bytes with the Sensirion CRC-8 (polynomial 0x31, initial value 0xFF, no reflection, nothing applied at the end). This is identical to the carbon dioxide sensor, and the same computation is written out again in this file so that each driver can be read on its own.

As with the other sensor, a command and its answer must be two separate exchanges. The combined write-then-read form is not accepted.

The one command that carries an argument

Starting a measurement requires stating the format the results should be reported in. That argument is a word, and like every word it needs its own check byte, so the frame sent is five bytes rather than two: 

byte   0      1      2      3      4
     +------+------+------+------+------+
     | 0x00 | 0x10 | 0x03 | 0x00 | 0xAC |
     +------+------+------+------+------+
      \___ command ___/\__ argument __/\_ CRC of the
        0x0010 =           0x0300 =       argument only
        start              floating-point
        measurement        output format

The alternative argument the sensor accepts is a compact integer format. Floating-point is chosen because it needs no scaling on this side.

The value 0x0300 appears twice in this file with two unrelated meanings: as the argument selecting floating-point output, and as the command that reads measured values. They are separate constants for that reason.

The sixty bytes returned by a measurement read

received: 60 bytes = 20 groups of (2 data bytes + 1 check byte)
             |
             |  strip_crc: verify every check byte, keep the data bytes
             v
          40 bytes = 10 groups of 4 bytes
             |
             |  each group of 4 bytes is one IEEE-754 floating-point number,
             |  most significant byte first
             v
          10 numbers, in this fixed order:

   0  pm1_0     1  pm2_5     2  pm4_0     3  pm10      4  nc0_5
   5  nc1_0     6  nc2_5     7  nc4_0     8  nc10      9  typical_particle_size

IEEE-754, briefly

The four bytes of each value are not a plain whole number. They are a standard arrangement of a sign, an exponent and a fraction that together encode a decimal number — the same arrangement the microcontroller itself uses. Because the two agree exactly, the four bytes are reinterpreted rather than converted, and no arithmetic is involved.

Continuous mode and the readiness flag

Once started, the sensor measures on its own about once per second. A one-word flag reports whether a result has appeared since the last one was collected. Reading measured values without checking the flag is permitted; it simply returns the previous result again.

Module description lines 1–12

//! Minimal driver for the Sensirion SPS30 particulate matter sensor.
//!
//! The sensor is used in its continuous measurement mode:
//!
//! 1. `start_measurement` (0x0010) starts the fan and the measurement loop.
//! 2. `is_data_ready` (0x0202) reports when a new result is available (~1/s).
//! 3. `read_measured_values` (0x0300) returns 10 IEEE-754 big-endian floats.
//!
//! Every word on the wire is big-endian and protected by a CRC-8 with
//! polynomial 0x31, initial value 0xFF, no reflection and no final XOR.

#![allow(dead_code)]
Documentation and one attribute

The //! lines describe the file as a whole and state the three steps the firmware actually performs, which is the minimum needed to compare this code against the datasheet.

"Continuous measurement mode" is the sensor's normal way of working: once started it measures repeatedly on its own schedule. The alternative would be to start and stop it around each reading, which is not done here because the fan needs time to reach a steady airflow.

#![allow(dead_code)] switches off the warning about items that are never used. Six items here are complete and correct but not called by this firmware: device_reset, start_fan_cleaning, sleep, wake_up, with_address and DEFAULT_ADDRESS. They are kept because they are documented behaviour of the sensor and would otherwise have to be written again when needed.

The suppression applies to the whole file, so a genuinely unused item added later will also not be reported.

The number that identifies this sensor among the devices sharing the two wires.

The comment says fixed rather than "factory default", and the difference is real: the SPS30 offers no way to change its address at all, so exactly one can be attached to a bus.

This is the address that appears in the start-up scan produced by src/drivers/i2c_bus.rs. If the line I2C device found at 0x69 is missing from the console, no command in this file can succeed and the fault is electrical rather than in this code.

The SPS30 needs a 5 volt supply for its fan and laser even though its two signal wires work at the microcontroller's lower voltage. A sensor with only the signal wires connected is silent.

Checksum settings lines 45–46

const CRC8_POLYNOMIAL: u8 = 0x31;
const CRC8_INIT: u8 = 0xFF;
Datasheet values

The two numbers defining the checksum used by every Sensirion sensor: the pattern combined into the running value, and the value the computation starts from.

They are the same two numbers as in src/drivers/scd41.rs. Repeating them rather than sharing them keeps each driver independent, so a change to one sensor's driver cannot affect the other.

A wrong value here would not produce an obvious failure. It would cause every reading to be rejected as corrupt, and the sensor would appear to be faulty.

Data structure

Two things can go wrong, and they mean different things:

  • Bus — the exchange itself failed. Nothing answered, or the transfer was cut short. Usually the sensor is absent, its 5 volt supply is missing, or it is asleep. The original hardware error is carried inside so it can be printed.
  • Crc — the sensor answered but a check byte did not match. The sensor is present and talking; the wiring is picking up interference.

This type is separate from the identically shaped one in the carbon dioxide driver. The two are deliberately not shared, and the task that uses this sensor imports this one by name.

The From block states how a hardware error becomes an Error::Bus. Once that exists, the question-mark operator used throughout the file performs the conversion automatically.

One reading: ten decimal numbers, forty bytes. The field order matches the order the sensor sends them in, so the decoding step below is a straight copy with no rearranging.

The units are stated in the comments in plain characters — ug/m3 for micrograms per cubic metre and um for micrometres — rather than with the Greek letter, because these comments appear in build output where non-English characters are not guaranteed to survive. Unlike the carbon dioxide sensor's reading, the values are stored exactly as received rather than as raw words needing conversion, because the sensor already reports them in their final units.

Eq is not among the derived properties, and cannot be: these are floating-point numbers, and the standard they follow declares that a value representing "not a number" is not equal even to itself. PartialEq is derived, which allows comparison without claiming that every value equals itself.

All forty bytes are kept in the history. Only the four mass values and the typical particle size are published by the web server; the five number concentrations are retained but not sent, to keep replies small.

The checksum computation lines 88–104

/// Compute the Sensirion CRC-8 over a data word.
fn crc8(data: &[u8]) -> u8 {
    let mut crc = CRC8_INIT;

    for byte in data {
        crc ^= byte;
        for _ in 0..8 {
            if crc & 0x80 != 0 {
                crc = (crc << 1) ^ CRC8_POLYNOMIAL;
            } else {
                crc <<= 1;
            }
        }
    }

    crc
}
Verification

Produces the check byte for a group of data bytes. Here it is always called with two bytes: the two halves of one word.

Step by step. The value starts at 0xFF. Each data byte is combined into it with an exclusive-or, which flips exactly the bits that byte has set. The value is then processed one bit at a time, eight times: if its highest bit is set, it is shifted left and the polynomial is combined in; otherwise it is only shifted. Whatever remains at the end is the check byte.

The property this gives is that a change to any single bit of the data produces a different check byte, which is what makes corruption detectable.

This function is character for character the same as the one in src/drivers/scd41.rs. The duplication is deliberate: it keeps the two drivers independent, and each is short enough that sharing it would create a dependency for no real saving.

Unlike the carbon dioxide driver, this one runs it twenty times per reading rather than three, and once more when sending the start argument — still trivial against a five-second interval.

Removing and checking the check bytes lines 106–119

/// Strip the CRC bytes from a raw `word + crc` stream, verifying each one.
///
/// `raw` must be a multiple of 3 bytes; `data` receives 2 bytes per triple.
fn strip_crc(raw: &[u8], data: &mut [u8]) -> Result<(), Error> {
    for (chunk, out) in raw.chunks_exact(3).zip(data.chunks_exact_mut(2)) {
        if crc8(&chunk[..2]) != chunk[2] {
            return Err(Error::Crc);
        }
        out[0] = chunk[0];
        out[1] = chunk[1];
    }

    Ok(())
}
Verification

Converts a stream of three-byte groups into a stream of two-byte words, checking every group on the way. This is where the carbon dioxide driver and this one differ in structure: that sensor always returns exactly three words, so its equivalent is fixed at nine bytes, whereas this one must handle three, forty-eight and sixty bytes, so the sizes are given by the caller.

chunks_exact(3) walks the received bytes in groups of three; chunks_exact_mut(2) walks the output in pairs; zip advances them together. No index arithmetic is written by hand, and if the two buffers do not correspond the shorter one simply ends the loop.

For each group the check byte is recomputed from the first two bytes and compared with the third. A single mismatch anywhere ends the function immediately with Error::Crc, and the caller discards the whole answer. A reading with one bad word is not partially usable.

The comment states the requirement the caller must meet: the received buffer must be a whole number of three-byte groups, and the output must have room for two bytes per group. Both callers in this file declare fixed-size buffers that satisfy this, so the requirement cannot be violated at run time.

The function returns nothing on success. Its result is the bytes it wrote into the output buffer.

/// SPS30 attached to an esp-hal I2C bus.
///

Data structure

The driver holds only a borrowed I2C block and the address to speak to. It stores nothing about the sensor, so creating one costs nothing and the driver's idea of the sensor cannot drift out of step with reality.

This is why the task creates a fresh Sps30 for every exchange — several times per reading, once for each readiness poll — rather than keeping one. The state that does exist, namely whether the sensor has been started, is held by the task.

The comment describes the timing behaviour precisely. Sending bytes occupies the processor until the transfer finishes. Waiting out an execution time does not: the task is suspended and others run.

'a and 'd record how long the borrowed block lives, so the driver cannot outlive it. T stands for whichever I2C hardware block is in use.

Sending one command lines 144–149

    /// Send a bare 16-bit command and wait for its execution time.
    async fn send_command(&mut self, command: u16, execution_delay_ms: u64) -> Result<(), Error> {
        self.i2c.write(self.address, &command.to_be_bytes())?;
        Timer::after_millis(execution_delay_ms).await;
        Ok(())
    }
Internal building block

Every command that carries no argument goes through these three lines.

to_be_bytes splits the 16-bit command into two bytes, most significant first: 0x0104 becomes [0x01, 0x04]. The name states the byte order, so it cannot be confused with the opposite convention.

The question mark is the early-return operator: if the exchange failed, the function stops immediately and the failure reaches the caller as Error::Bus. The wait is then skipped, which is correct, because a command that was never delivered is not being executed.

Timer::after_millis(...).await suspends the calling task for the execution time. Other tasks run during it.

The function is private. Callers ask for operations by name, and the command code and its execution time are supplied together here so the two cannot be mismatched.

Sending a command with an argument lines 151–171

    /// Send a 16-bit command followed by one CRC-protected argument word.
    async fn send_command_with_argument(
        &mut self,
        command: u16,
        argument: u16,
        execution_delay_ms: u64,
    ) -> Result<(), Error> {
        let command = command.to_be_bytes();
        let argument = argument.to_be_bytes();

            command[0],
            command[1],
            argument[0],
            argument[1],

        Timer::after_millis(execution_delay_ms).await;
        Ok(())

Internal building block · used once

Builds the five-byte frame shown in the protocol section above and sends it in one exchange. Only start_measurement uses this.

The checksum covers the argument alone. crc8(&argument) is computed from the two argument bytes and nothing else. The command bytes are not protected, which is the rule these sensors follow: commands are unprotected, data words are protected. Including the command bytes in the computation would produce a check byte the sensor rejects.

Both halves are converted to bytes with the same most-significant-first ordering used everywhere else, and the five bytes are assembled into a fixed-size array on the stack.

The whole frame goes out as a single exchange. Splitting it into two would leave the sensor with a command whose argument never arrived.

The final two lines are identical to send_command: report a failure at once, otherwise wait the execution time.

Internal building block

Three lines that every read in this file uses: send the command, collect the raw bytes, verify and unpack them.

The buffers are supplied by the caller, and their sizes decide how much is read. The hardware driver reads exactly enough bytes to fill the buffer it is given, so a three-byte buffer reads the readiness flag and a sixty-byte buffer reads a full measurement, with no length parameter needed.

The comment records a protocol requirement, not a preference. The usual efficient approach keeps hold of the bus between the command and the answer using a repeated START. This sensor does not accept that: the command must be a finished exchange before the answer is requested in a second one. Using the combined form would produce no answer at all.

Every read uses the same five-millisecond pause, including the sixty-byte one, because that pause is a property of the sensor rather than of the amount of data.

Called by the task during initialisation

Starts the fan and the measurement loop, and selects floating-point output. From this point the sensor produces a new result about once a second until it is stopped.

The comment states three different timescales, and the difference matters when reading the output.

  • 20 milliseconds — the command itself is finished and the sensor accepts the next one.
  • About 1 second — the first result appears and can be read.
  • About 30 seconds — the airflow through the sensor has settled and the values can be trusted.

Only the first is waited for here. The firmware publishes readings from the first second onwards, so the first few entries after a restart may be inaccurate. They are kept rather than discarded, because the history records the timestamps and a gap would be harder to interpret than a slightly wrong start.

The sensor rejects this command while it is already measuring, which happens whenever the microcontroller restarts and the sensor does not. The task therefore sends a stop first, ignoring its result, and only then starts.

Reset restarts the sensor, which returns idle after 100 milliseconds. It is the heaviest recovery step available. The task does not use it: sending a stop and then a start achieves the same result and is quicker.

Fan cleaning runs the fan at full speed for ten seconds to blow accumulated dust off the optics. The manufacturer recommends it weekly for continuously running sensors. It only starts the routine; the command finishes in 20 milliseconds while the fan continues for ten seconds, during which readings are meaningless.

Cleaning is not scheduled by this firmware. Adding it would mean choosing a moment, suppressing the readings taken during it, and recording that they were suppressed — decisions belonging to the task, not to this file.

Not used by this firmware

Sleep puts the sensor into a low-power state. The comment records the restriction: it is only accepted while idle, so a running measurement must be stopped first.

Waking needs the unusual treatment the comment explains. A sleeping SPS30 does not acknowledge its address at all, so the first attempt cannot succeed — but receiving it is what rouses the sensor's interface. The command is therefore sent twice:

  1. The first write is expected to fail, and its result is deliberately discarded with let _ =. Its only purpose is to rouse the sensor.
  2. Five milliseconds are allowed for that to happen.
  3. The second write is the real one. Its result is returned, so a sensor that is genuinely absent still reports a failure.

Discarding the first result is essential. Using the question-mark operator there would return a failure in exactly the case the function is designed to handle.

The firmware never puts this sensor to sleep, because a sleeping particle sensor measures nothing and its fan needs about thirty seconds to give trustworthy readings after waking.

Called by the task, up to 30 times per reading

The smallest exchange in the file: one word, three bytes on the wire.

The sensor returns 0x0001 when a result has appeared since the last one was collected, and 0x0000 otherwise. The first byte is always zero and carries no information, which is why only data[1] is examined.

The comparison is against 0x01 exactly, rather than testing for any non-zero value. Only the two documented values can occur, and an undocumented one is treated as "not ready", which is the safe interpretation: it causes another poll rather than a reading that may not exist.

The check byte is verified like any other, so a corrupted flag produces Error::Crc rather than a false answer.

The task calls this up to thirty times, a tenth of a second apart, releasing the shared bus between each. If none of them reports a result, it reads the values anyway — the previous result is better than no entry in the history, and a genuine fault still shows up as an error from the read itself.

The serial number lines 243–254

    /// Read the ASCII serial number; useful as a presence check.
    ///
    /// Returns the NUL-terminated buffer and the number of characters in it.
    pub async fn serial_number(&mut self) -> Result<([u8; SERIAL_NUMBER_LEN], usize), Error> {
        let mut raw = [0u8; 3 * SERIAL_NUMBER_LEN / 2];
        let mut data = [0u8; SERIAL_NUMBER_LEN];
        self.read_response(CMD_READ_SERIAL_NUMBER, &mut raw, &mut data)
            .await?;

        let len = data.iter().position(|&byte| byte == 0).unwrap_or(data.len());
        Ok((data, len))
    }
Called by the task during initialisation

Reads the sensor's identifier, which unlike the carbon dioxide sensor's is text rather than a number — a run of printable characters such as "6E9C1B4A2D3F8E70".

3 * SERIAL_NUMBER_LEN / 2 is 48: thirty-two characters occupy sixteen words, and each word costs three bytes on the wire. Writing the arithmetic rather than the number keeps the two buffers in step if the length is ever changed.

The text is padded with zero bytes to the full thirty-two, so its real length has to be found. position returns where the first zero byte is, and unwrap_or(data.len()) covers the case where there is none, treating the whole buffer as text. Without that fallback a sensor returning thirty-two characters and no terminator would have no length to report.

Both the buffer and the length are returned, because the buffer has a fixed size and only the caller's use of the length makes the unused remainder harmless. The task combines them into text and prints SPS30 found, serial number: ....

As with the other sensor, the value itself is not used. Reading it successfully proves the sensor is powered, holds the expected address, accepts commands, and produces correct checksums.

The largest exchange in the file: sixty bytes received, forty kept.

The two buffers are declared with their sizes written out rather than computed, because both are fixed by the sensor: twenty words of three bytes, holding ten values of four bytes.

The warning in the comment matters. This command always answers, whatever state the sensor is in. In idle mode it returns the last result taken before the fan stopped, or zeros if none was ever taken. There is no error and no indication that the values are stale, so it is the caller's responsibility to ensure a measurement is running.

The one-in, one-out arrangement means a caller cannot receive half a reading: either all twenty check bytes matched and all ten values are present, or an error is returned and nothing is.

Decoding

Turns the forty verified bytes into ten decimal numbers. This is done in two steps, and the distinction between them is worth being precise about.

  • u32::from_be_bytes assembles four bytes into one 32-bit whole number, the first byte contributing the highest part. This is the same most-significant-first ordering used everywhere else in the protocol.
  • f32::from_bits then reinterprets those same 32 bits as a decimal number. It performs no arithmetic and changes no bit; it only states that the bits should now be read according to the IEEE-754 arrangement of sign, exponent and fraction.

This works because the sensor and the microcontroller both use that same standard arrangement, so no conversion is required — only agreement about the byte order, which the sensor states and this code follows.

The alternative, treating the whole number as a value and converting it, would produce numbers in the billions rather than the sensor's readings. The two operations look similar and are entirely different.

chunks_exact(4) walks the buffer in groups of four and zip pairs each with its destination, so the loop runs exactly ten times.

The reading handed to the rest of the firmware

Labels the ten numbers. The order is fixed by the datasheet and this list is the only place in the firmware where it is recorded.

It is written out one field at a time rather than copied wholesale, because that is what makes the order checkable against the datasheet by eye. An error here would produce readings that look entirely plausible — mass values in the right range, in the wrong fields — and would be very hard to notice afterwards.

Note the two different series interleaved in one list: positions 0 to 3 are masses in micrograms per cubic metre, positions 4 to 8 are counts per cubic centimetre, and position 9 is a size in micrometres. The names carry the distinction, since the numbers themselves do not.

From here the reading travels unchanged into the history in external memory, and five of its ten fields are eventually written into the web server's replies.
