src/tasks/blink_task.rs — LED liveness indicator

This task repeatedly changes the user LED output between high and low levels. Its only purpose is to provide a visible indication that the firmware scheduler is still running.

What this file does

This file defines one Embassy task: blink_task. The task receives exclusive control of an already-configured general-purpose output pin, raises the output level for 500 milliseconds, lowers it for 500 milliseconds, and repeats indefinitely.

The LED is not used to control sensors, Wi-Fi, data storage, or the web server. It is an independent health indicator. If it continues to blink, the Embassy executor is still scheduling this task and the timer service is operating.

main.rs spawns this task first — before Wi-Fi is started and before any of the nine sensor tasks — precisely so that a hang inside one of those subsystems still leaves a visible signal that the executor itself is alive.

A blinking LED does not prove that every other firmware component is working. For example, an I²C sensor may fail while this task continues normally. It proves only that this task can run and wait on its timer.

The task has no return value and no network, storage, or sensor inputs. It does not touch the shared I²C bus, so it can never be delayed by a sensor and can never delay one. After it receives the output controller, it owns that controller for the rest of the program run.

Operation over time

Imports lines 1–2

use embassy_time::Timer;
Dependency

Timer is the asynchronous delay type from embassy_time. It is the only thing this file needs from that crate.

It does not measure time itself. It reads the hardware timer that main.rs installed with esp_hal_embassy::init(clocks, timers), which is driven by the first timer of timer group 0. If that initialisation had not happened before this task was spawned, the waits below could not complete.

use esp_hal::gpio::{AnyPin, Output};
Dependency

Output is the type that drives one pin electrically high or low. Owning an Output is what gives this task the right to change the pin; there is no global "set pin 21" function.

AnyPin is the type-erased form of a GPIO pin. Pins normally carry their number in their type, for example GpioPin<21>, which would fix the LED pin inside this file. AnyPin moves that choice out to the caller, so the same task can blink any pin.

Both names appear only in the task's parameter type. Neither is constructed here; main.rs builds the value and hands it over.

Blink timing lines 4–5

/// Half period of the liveness blink.
Documentation comment

Three slashes make this a documentation comment attached to the item on the next line, rather than an ordinary // comment. It is compiled into the crate's generated API documentation.

It states the meaning precisely: this is the half period, not the full blink period. The value is used twice per cycle, so the full cycle is twice this number.

const LED_BLINK_INTERVAL_MS: u64 = 500;
Configuration

500 milliseconds at each output level: high for half a second, then low for half a second. One complete cycle therefore takes 1,000 milliseconds, and the pin changes level twice per second.

const means the value is substituted wherever the name appears when the program is compiled. It occupies no memory of its own at run time and cannot be changed while the firmware runs.

The type is u64 because that is what Timer::after_millis accepts. Writing it as a typed constant means the two call sites below cannot drift apart: changing this one number changes both halves of the cycle together.

It is not marked pub, so nothing outside this file can read it. No other file needs to know the blink rate.

The task lines 7–19

/// Blink the configured user LED.
///
/// On boards where the LED is wired active-low, the visible on/off states are
/// reversed, but the blink still confirms that the executor keeps running.
Documentation comment

The first line is the summary. The blank comment line separates it from the body, which is the convention Rust's documentation tool expects.

The body records the one thing a reader could get wrong. Active-low wiring means the LED is connected between the supply and the pin, so it lights when the pin is pulled low. On such a board the LED is lit during the set_low() half, which is the opposite of what the code appears to say.

The comment then makes the point that this does not matter: the purpose of the task is to prove the executor is still scheduling work, and an inverted blink proves that just as well as an upright one. This file deliberately does not try to detect or correct the wiring polarity.

#[embassy_executor::task]
Attribute

This attribute rewrites the function below into something the Embassy executor can start. Without it, spawner.spawn(blink_task::blink_task(led)) in main.rs would not compile.

What it generates is a fixed-size storage slot for this task's state. The firmware has no heap, so the memory a task needs while it is suspended cannot be allocated on demand; it has to be reserved when the program is compiled. The attribute reserves exactly one slot here, because the default pool size is one, which means this task may be spawned only once. A second spawn would fail at run time, not at compile time.

That failure would be reported. main.rs does not discard the spawn result: it passes it to its spawn_task helper, which prints SPAWN FAILED: blink (…) on the console.

pub async fn blink_task(mut led: Output<'static, AnyPin<'static>>) {
External interface · called by main.rs

pub is required because main.rs spawns it from another module.

async means the function can suspend at an await and be resumed later. It returns nothing and, because of the endless loop below, never returns at all.

mut led — the parameter is taken by value, not by reference. The Output is moved into the task and stays there for the rest of the program run. Once main.rs has passed it, main.rs no longer holds it, and any attempt to drive the same pin elsewhere is rejected when the program is compiled. This is what enforces single ownership of the LED pin. It must be mut because set_high and set_low take &mut self.

The two 'static lifetimes say the pin and its type-erased handle are valid for the whole run. A spawned task can outlive whatever spawned it, so it may not hold anything shorter-lived; 'static is the only lifetime that satisfies that.

In the current firmware main.rs constructs the argument as Output::new(AnyPin::new(io.pins.gpio21), Level::Low) — GPIO21, starting low — and spawns this task before Wi-Fi and before any sensor task, so that a later hang in one of those subsystems still leaves a visible signal that the executor itself is alive.
    loop {
Control flow

An endless loop with no exit condition and no break. Rust knows it never finishes, so no value has to be returned after it.

This is the normal shape of an Embassy task. A task that returned would free its slot and simply stop existing, and the LED would freeze at whatever level it last held.

Nothing is allocated and no lock is taken inside the loop, so this task can never run out of memory and can never block another task by holding a resource. It is the cheapest possible proof of life.

        led.set_high();
Pin write

Drives the pin to the supply voltage. This is a direct write to a hardware register: it takes a handful of processor cycles, cannot fail, and returns nothing.

There is no await here, so the task does not yield; it continues straight to the next line.

Whether this lights the LED depends on the wiring, as the documentation comment above explains.

        Timer::after_millis(LED_BLINK_INTERVAL_MS).await;
Yield point

Waits 500 milliseconds. This is the first of the two suspension points in the task, and the pin stays high throughout.

Timer::after_millis(500) only describes the wait; it does nothing on its own. The .await is what hands control back to the executor, which registers a wake-up 500 ms from now and then runs whichever other task is ready. Nothing here spins or counts cycles, so the nine sensor tasks and the web server are not delayed.

The delay is measured from the moment the timer is created, not from the last blink, so a busy executor makes the cycle slightly longer than one second rather than accumulating a fixed drift.

        led.set_low();
Pin write

Drives the pin to 0 V — the mirror of set_high() above, and equally immediate.

This runs only after the executor has resumed the task, which is the fact the blink actually demonstrates: the task was suspended, the timer fired, and it was scheduled again.

        Timer::after_millis(LED_BLINK_INTERVAL_MS).await;
Yield point

The second wait, identical to the first, with the pin held low. Using the same constant for both is what makes the cycle symmetrical — a 50 % duty cycle.

After this the loop restarts. The total period is 500 ms + 500 ms = 1,000 ms, of which the task is suspended for essentially all of it; its own execution time per cycle is two register writes.

    }
}
Block ends

The first brace closes the loop, sending control back to led.set_high(). The second closes the function body, which is never reached.

Behaviour and limits

SituationResult
Normal operationThe output alternates every 500 ms. A visible LED normally appears to blink once per second.
Active-high LED wiringA high output level normally turns the LED on and a low level turns it off.
Active-low LED wiringThe visible states are reversed: high normally turns the LED off and low turns it on. The timing and diagnostic value remain the same.
Another task is ready while this task waitsThe executor can run that task. The timer wait is asynchronous rather than a processor-blocking delay.
LED wiring fault or failed LEDThe firmware may still be running even though no visible blink occurs. Serial diagnostics and the web interface must be used to distinguish this from a stopped device.
Timer service is not initializedThe waits cannot complete correctly. The firmware entry point initializes Embassy time before it starts this task.
The task is spawned a second timeThe second spawn fails at run time, because the attribute reserves exactly one storage slot. main.rs prints SPAWN FAILED: blink. The first task is unaffected.
The executor is busy with other workEach half-cycle becomes slightly longer than 500 ms. The delay is measured from when each timer is created, so the error does not accumulate into a growing drift.
The task assumes that it is spawned once and is the sole owner of the output controller. Creating a second controller for the same pin elsewhere would violate the intended hardware ownership model.
