src/tasks/blink_task.rs — LED liveness indicator

This task repeatedly changes the user LED output between high and low levels. Its only purpose is to provide a visible indication that the firmware scheduler is still running.

What this file does

This file defines one Embassy task: blink_task. The task receives exclusive control of an already-configured general-purpose output pin, raises the output level for 500 milliseconds, lowers it for 500 milliseconds, and repeats indefinitely.

The LED is not used to control sensors, Wi-Fi, data storage, or the web server. It is an independent health indicator. If it continues to blink, the Embassy executor is still scheduling this task and the timer service is operating.

A blinking LED does not prove that every other firmware component is working. For example, an I²C sensor may fail while this task continues normally. It proves only that this task can run and wait on its timer.

Timer provides the asynchronous delay used between level changes. The delay is tied to the time service initialized by the firmware entry point.

Output is the type that can drive a pin high or low. AnyPin allows the task to accept an output for any physical GPIO pin, rather than only a pin number fixed in this file.

Pin selection belongs outside this task. In the current firmware, main.rs selects GPIO21 and creates the Output before spawning this task.

Blink timing lines 4–5

/// Half period of the liveness blink.
  const LED_BLINK_INTERVAL_MS: u64 = 500;
Configuration

This constant is the duration of each visible state: high for 500 milliseconds, then low for 500 milliseconds.

A complete blink takes one second: the LED remains at each output level for half a second. Its output level changes twice during that second.

Using a named constant prevents the two waits in the task from diverging accidentally. Changing the constant changes both halves of the cycle together.

The task lines 7–18

/// Blink the configured user LED.
  ///
  /// On boards where the LED is wired active-low, the visible on/off states are
  /// reversed, but the blink still confirms that the executor keeps running.
  #[embassy_executor::task]
  pub async fn blink_task(mut led: Output<'static, AnyPin<'static>>) {
    loop {
      led.set_high();
      Timer::after_millis(LED_BLINK_INTERVAL_MS).await;
      led.set_low();
      Timer::after_millis(LED_BLINK_INTERVAL_MS).await;
    }
  }
Task body

#[embassy_executor::task] allows the Embassy executor to start this asynchronous function as a task. It is not an operating-system thread. On this single-core firmware, it runs until it reaches an await, then allows other ready tasks to execute.

The mut led parameter is mutable because both set_high() and set_low() change the output controller's state. Its 'static lifetime means the controller remains valid for the entire firmware run.

The loop has no exit path. The task alternates the electrical level, waiting after each change. No memory is allocated and no shared lock is acquired.

Timer::after_millis(...).await is a waiting point. The task is dormant until the interval has elapsed; it does not run a busy loop and does not intentionally occupy the processor during the 500 ms delay.

Behaviour and limits

SituationResult
Normal operationThe output alternates every 500 ms. A visible LED normally appears to blink once per second.
Active-high LED wiringA high output level normally turns the LED on and a low level turns it off.
Active-low LED wiringThe visible states are reversed: high normally turns the LED off and low turns it on. The timing and diagnostic value remain the same.
Another task is ready while this task waitsThe executor can run that task. The timer wait is asynchronous rather than a processor-blocking delay.
LED wiring fault or failed LEDThe firmware may still be running even though no visible blink occurs. Serial diagnostics and the web interface must be used to distinguish this from a stopped device.
Timer service is not initializedThe waits cannot complete correctly. The firmware entry point initializes Embassy time before it starts this task.
The task assumes that it is spawned once and is the sole owner of the output controller. Creating a second controller for the same pin elsewhere would violate the intended hardware ownership model.
