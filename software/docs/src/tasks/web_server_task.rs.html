What this file does

This one file contains everything the device needs to be reachable from a web browser on your home network. It does three separate jobs, each running as its own independent task:

  1. Join the Wi-Fi network. The board behaves like a phone or laptop: it connects to an existing wireless router using a network name and password that were compiled into the firmware. It does not create its own hotspot.
  2. Run the network stack. The library that implements IP, TCP and DHCP only performs work while a task calls it, so one task exists to call it continuously.
  3. Answer HTTP requests. A server listens on TCP port 80 and replies to exactly three addresses: the web page itself, a small status report, and pages of stored sensor readings.

The file stores nothing itself. All the measured data lives in a separate module, utils/shared_state.rs, which the two sensor tasks write into and this file only ever reads from. This file converts that stored data into HTTP responses.

Constraints that shaped the implementation

  • No memory is allocated while running. There is no heap allocator in this firmware, so every buffer used here is a fixed-size area reserved at compile time. That is why responses are written out in small pieces instead of being assembled into one big string.
  • One client at a time. A single connection is accepted, answered, and closed before the next one is accepted. This keeps memory use to two 1536-byte buffers.
  • The device keeps no per-client state. It does not record which client has received which readings. Each reading has a number that never repeats, so a browser requests "everything from number N onwards" and the device answers using only that number.
  • The device has no clock. There is no battery-backed real-time clock on the board, so readings are timestamped with "milliseconds since the board powered on". Every response also reports the current uptime, which lets the browser convert those numbers into real dates using its own clock.

Two guarantees about this reply. First, the array always contains exactly count elements, so the element at position i is always the reading numbered from + i, including when some positions are null. Second, a from value naming a reading that has already been overwritten is moved forward to the oldest retained reading without returning an error, and the value actually used is reported in the from field, so the client can determine that some readings were not received.

The SPS30 sensor measures more values than are published here (particle counts for several size classes). Only the mass concentrations and the typical particle size are sent, to keep replies small. The SCD41 temperature and humidity are stored as raw sensor words and converted to real units at the moment they are written into the reply.

Imports

Each line makes a name from another package usable here. Two of them use the as _ form:

  • core::fmt::Write as _ — imported "anonymously". It is never referred to by name; it exists only so that the write! macro can append formatted text into a text buffer. This is text formatting.
  • embedded_io_async::Write as _ — likewise anonymous, and this one is what makes socket.write_all(...) available. This is writing bytes to the network. Two different things happen to share the name "Write"; importing them anonymously is how both can be used in the same file without a name clash.

heapless::String is a text buffer whose maximum size is fixed when the program is compiled, for example String<512> holds at most 512 bytes. It cannot grow. Appending more text than fits discards the excess and returns an error rather than requesting memory from a heap, because this firmware has no heap.

crate::utils::shared_state is the only project-internal dependency: the module holding the stored sensor readings.

option_env! looks up an environment variable while the firmware is being compiled, not while it runs. Whatever value the variable had at that moment is baked into the binary as fixed text.

Configuration
  • HTTP_PORT = 80 — the port the server listens on.
  • INDEX_HTML — include_str! reads src/tasks/web/index.html at compile time and pastes its entire contents into the program as one long piece of text. At run time there is no file and no filesystem; the page is a constant stored in flash memory. Editing that HTML file requires rebuilding and reflashing.
  • SOCKET_COUNT = 3 — how many network sockets the stack is allowed to track at once. The web server uses one; the remainder cover DHCP and connections in the process of being closed. This value is exported so main.rs can size the stack's memory to match.
  • RECONNECT_DELAY_MS = 5000 — wait five seconds before retrying a failed Wi-Fi connection, so that at most one connection attempt is made every five seconds while a router is unavailable.
  • SOCKET_TIMEOUT_S = 10 — drop a connection that has gone ten seconds without traffic. Without this, a client that stops responding would hold the single available connection indefinitely and no further request would be answered.
  • MAX_PAGE_READINGS = 2000 — the maximum number of readings one request may return, regardless of what the client asks for. A full day of SPS30 readings is 17,280 entries; sending them in one reply could exceed the ten-second connection timeout, so the client requests them in several smaller pages instead.

Connection buffers lines 66–69

/// Receive buffer for one client connection.
static mut RX_BUFFER: [u8; 1536] = [0; 1536];
/// Transmit buffer for one client connection.
static mut TX_BUFFER: [u8; 1536] = [0; 1536];
Memory

Two fixed 1536-byte areas of memory, reserved for the entire life of the program. TCP needs somewhere to hold bytes that have arrived but not yet been read, and bytes that have been written but not yet acknowledged by the other side; these are those places.

1536 is chosen to be slightly more than the 1500-byte maximum size of a single Ethernet/Wi-Fi packet, so a full packet always fits.

static mut means "one single global, changeable copy". Rust treats globals that can change as dangerous, because two tasks touching one at the same time would corrupt it. That is why the code that picks them up (further below) has to be explicitly marked as unchecked, together with a written justification: only one task ever exists that uses them.

The #[embassy_executor::task] marking turns this function into something that can be started as an independent task. Tasks here are not operating-system threads: they all run on the single processor core, and each one runs until it reaches a point where it must wait, at which moment another task gets to run. That switching point is always an await.

controller is the object that commands the radio. It is created in main.rs and handed over here permanently; nothing else can command the radio afterwards.

If no network name was compiled in, there is no network to connect to. The task prints one line to the serial console and returns, which ends the task permanently. The rest of the firmware — sensor reading, the LED, storing history — continues to run; only network access is unavailable.

A loop that repeats for as long as the program runs, supervising the connection.

If the radio is already associated with the router, no action is required, so the task waits for the radio to report a disconnection. While waiting it consumes no processor time; other tasks run instead. It resumes only when the connection drops.

After a disconnection it waits five seconds before continuing to the reconnection code below. Without that delay the board would retry continuously and produce hundreds of failed attempts per minute while the router is still unavailable.

        if !matches!(controller.is_started(), Ok(true)) {

                ssid: SSID.try_into().unwrap(),

            if let Err(error) = controller.set_configuration(&configuration) {

                Timer::after_millis(RECONNECT_DELAY_MS).await;

This block only runs if the radio has not been powered up and configured yet — normally just once, right after boot.

Configuration::Client selects client (station) behaviour rather than hotspot behaviour. The network name and password are copied into fixed-size fields inside the radio driver; unwrap() causes the program to stop with an error message if they are too long to fit (over 32 characters for a network name, 64 for a password). This can only be caused by an incorrect build-time setting, not by anything received from the network.

..Default::default() fills in every remaining setting (security mode, channel selection, and so on) with its standard value.

If the driver rejects the settings, the error is printed, the task waits five seconds, and continue jumps back to the top of the loop to try again from scratch.

start() powers up the radio hardware. Like every other step, a failure is printed, followed by a five-second pause and a fresh attempt.

connect() performs the actual association with the router: scanning for the named network, authenticating with the password, and joining. Success or failure is reported on the serial console — these printed lines are the primary way to diagnose a device that will not come online.

After a successful association the loop returns to the top, finds that the radio is connected, and waits for a disconnection event. From that point reconnection is automatic: a router restart, a temporary loss of signal, or a re-authentication are all recovered without a manual reset.

Association is only step one. Being joined to the router does not yet mean having an IP address — that arrives via DHCP, which is handled by the next task.

/// Drive the embassy-net stack; it does no work unless this task runs.

The networking library is not a background service and has no thread of its own. All of its work — reading incoming radio frames, reassembling IP packets, retransmitting lost TCP data, requesting and renewing the DHCP address lease, answering ARP requests — happens inside stack.run(). That call does not return; it processes events and then waits for the next event, for as long as the program runs.

If this task were not started, the device would still be associated with the router but would never obtain an IP address and would never respond to anything.

Two conditions are waited for, in order, before the server can accept connections:

  • Link up — the radio is associated with the router. Set by the first task.
  • Address assigned — the router's DHCP server has handed out an IP address. Handled by the second task.

Both are checked twice a second. This adds at most 500 ms of delay, once, during startup.

When the address arrives it is printed as a complete URL, for example Web server: http://192.168.1.57/. The device has no display and the address is assigned by the router, so this serial output is the normal way to learn which address to open in a browser.

Why "unsafe" appears here

The compiler cannot prove on its own that nobody else is using those two global buffers, so it refuses to hand out exclusive access to them. The unsafe block is the programmer taking responsibility for that guarantee instead, and the comment above it states the reason: this task is started exactly once in main.rs, so no second user can exist.

The socket is created once and reused for every client that connects. The memory used by the server is therefore always the same two 1536-byte buffers, regardless of how many clients have been served.

The ten-second inactivity timeout applies to each connection. A client that connects and then sends nothing is disconnected, so a stalled client cannot hold the single socket indefinitely.

            socket.abort();

        socket.close();
        let _ = socket.flush().await;
        socket.abort();
        let _ = socket.flush().await;
    }
}

accept(80) waits for a browser to open a connection to port 80. While waiting, this task uses no processor time.

Once a connection exists, serve_connection reads the request and writes the complete reply. The loop only repeats after it returns, so exactly one client is served at a time. A second client that connects during that period waits until the current reply is finished.

The four teardown steps, and what each one does:

  • close() begins an orderly shutdown, telling the browser "that is the end of the data". For /api/readings, which sends no length in advance, this is how the browser learns the response is complete.
  • the first flush() waits for the remaining bytes to actually leave.
  • abort() then forcibly resets the connection, discarding any lingering state such as data the browser sent that was never read.
  • the second flush() waits for that reset to be sent.

Without the forced reset the socket would remain in a half-closed state and the next client would not be answered. Because there is only one socket, it must be returned to an unused state after every connection.

Reading and routing one request lines 181–242

async fn serve_connection(socket: &mut TcpSocket<'_>) {
    let mut request = [0u8; 512];
    let mut filled = 0;

    // Read until the end of the header block; the request has no body.
    loop {
        match socket.read(&mut request[filled..]).await {
            Ok(0) => return,
            Ok(count) => {
                filled += count;
                if request[..filled].windows(4).any(|w| w == b"\r\n\r\n") {
                    break;
                }

A 512-byte scratch area on the task's own stack holds the incoming request. filled counts how much of it has been used.

Data arrives in arbitrarily sized chunks, so the code reads repeatedly, always into the still-empty part of the buffer (request[filled..]), until it finds the marker that ends an HTTP header block: a blank line, written as the four bytes carriage-return, line-feed, carriage-return, line-feed. That is what windows(4).any(...) searches for — it slides a four-byte window across everything received so far and checks each position.

A read result of zero means the browser closed the connection without sending anything, so the function returns without replying and the outer loop waits for the next client.

Only GET requests are supported, and GET requests carry no body, so there is nothing to read after the blank line.

                if filled == request.len() {

                        .await;
                    return;
                }
            }
            Err(error) => {
                println!("Web server: read failed: {:?}", error);
                return;
            }
        }
    }
Safety boundary

This is the limit on request size. If 512 bytes arrive without the blank line appearing, the buffer is full and reading must stop; continuing would either write past the end of the buffer or loop without terminating. The device replies 431 and closes the connection.

Because the buffer is a fixed-size array and every read is limited to the space remaining in it, no quantity of data sent by a client can be written past its end.

512 bytes is enough for the requests the built-in page makes, but a browser sending unusually large headers, for example many cookies, can exceed it and receive a 431.

A read error — the connection dropped part-way through the request — is printed and the function returns; no reply can be delivered over a connection that has already failed.

The received bytes are interpreted as text. If they are not valid text, the result becomes an empty string rather than an error, and the request then fails the method check a few lines below.

An HTTP request starts with a line such as GET /api/status?sensor=scd41 HTTP/1.1. Splitting on spaces and taking the first two pieces yields the method (GET) and the target (/api/status?sensor=scd41). Missing pieces become empty strings, so a truncated request cannot cause a crash.

Anything that is not a GET is refused with 405, and the Allow: GET header states what is permitted. The device provides no HTTP request that writes, configures or resets anything; all three endpoints are read-only.

The complete routing table

The target is split at the first question mark into the path and the query string. A target with no question mark yields an empty query string.

The path is then compared against exactly four cases. This is the entire public surface of the device:

  • / and /index.html both serve the page.
  • /api/status serves the summary.
  • /api/readings serves stored measurements; it is the only handler that is given the query string, because it is the only one with parameters.
  • Everything else is 404 Not Found.

The comparison is exact and literal. There is no directory traversal, no file lookup and no pattern matching, so a request for something like /../../secret is just another unmatched string that produces a 404.

Reading one query parameter lines 244–254

fn query_param<'a>(query: &'a str, name: &str) -> Option<&'a str> {
    query.split('&').find_map(|pair| {
        let (key, value) = pair.split_once('=')?;
        (key == name).then_some(value)
    })
}

Given a query string such as sensor=scd41&from=100&limit=50 and a name such as from, this returns the matching value ("100") or nothing if that name is absent.

It splits on & to get each key=value pair, then on the first = to separate the two halves, and returns the value of the first pair whose key matches. A fragment without an = is skipped.

No memory is copied: the returned text points directly into the original request buffer, which is why the function is written with an explicit lifetime marker 'a tying the result's validity to the input's.

Percent-escapes such as %20 are not decoded. The source comment gives the reason: every parameter this server accepts is either a plain number or one of two fixed sensor names, and none of those can contain a character that requires escaping. A value that does contain an escape fails to match a known sensor name, or fails to parse as a number, and is handled by the error paths that already exist.

async fn send_response(socket: &mut TcpSocket<'_>, content_type: &str, body: &str) {
    let mut header: String<192> = String::new();
    let _ = write!(
        header,
        "HTTP/1.1 200 OK\r\nContent-Type: {}\r\nContent-Length: {}\r\n\
         Cache-Control: no-store\r\nConnection: close\r\n\r\n",
        content_type,
        body.len()
    );

    if socket.write_all(header.as_bytes()).await.is_ok() {
        let _ = socket.write_all(body.as_bytes()).await;
    }
}

Builds a complete HTTP response for the cases where the entire reply is already available as one piece of text.

The header is assembled in a 192-byte fixed buffer, which is longer than the header block this function produces for either of the two content types used. Each header line states one thing:

  • Content-Type — how the browser should interpret the body.
  • Content-Length — the exact byte count that follows, so the browser knows when the body is finished without waiting for the connection to close.
  • Cache-Control: no-store — the browser must not keep a copy. Without it a browser could redisplay a previously stored reply instead of requesting a current one.
  • Connection: close — this connection carries one request only, which matches the server, where the single socket is reset after every client.

The blank line at the end (\r\n\r\n) separates headers from body — the same marker the request parser searched for earlier.

The body is only sent if the header was sent successfully. Write failures are ignored: if the client has disconnected there is no recovery action to take, and the outer loop resets the socket in either case.

Calls into shared_state.rs

This is the endpoint the page requests repeatedly. It is small, its length is known in advance, and it contains everything a client needs in order to determine which readings it is missing before requesting any of them.

Three pieces of information are gathered: the current uptime, and a summary for each of the two sensors. Each summary is copied out of the shared storage while a lock is held; the lock is released before anything is sent to the network, so a slow client cannot block the sensor tasks.

The JSON is written by hand into a 512-byte fixed buffer. There is no JSON library involved. In the format string, {{ and }} produce single literal braces, because a single brace would mean "insert a value here", and \" produces a literal double quote.

Every write result is discarded with let _ =. These writes can only fail by exhausting the buffer, and the output has a fixed set of fields whose longest possible form is shorter than 512 bytes, so that failure cannot occur.

Why uptime is included: readings are timestamped with the uptime at which they were taken. The browser records its own wall-clock time when a reply arrives, subtracts the reported uptime, and thereby learns what real time the board started at. Every reading can then be placed on a real calendar timeline despite the board having no clock.

fn write_sensor_status(
    body: &mut String<512>,
    name: &str,
    status: &shared_state::HistoryStatus,
) -> core::fmt::Result {
    write!(
        body,
        "\"{}\":{{\"interval_ms\":{},\"capacity\":{},\"len\":{},\
          \"first_sequence\":{},\"next_sequence\":{}}}",
        name, status.interval_ms, status.capacity, status.len,
        status.first_sequence, status.next_sequence
    )
}

Writes one sensor's entry into the JSON object, so the same layout does not have to be typed twice.

The five numbers come from shared_state.rs and describe a ring buffer — storage of fixed size where, once full, each new reading overwrites the oldest one:

  • interval_ms — how often this sensor is scheduled to measure. The SCD41 measures every 10,000 ms and the SPS30 every 5,000 ms. The page uses this to tell a genuine gap in the data apart from normal spacing between points.
  • capacity — how many readings fit; zero means the storage could not be reserved at startup and nothing is being retained.
  • len — how many are held right now.
  • first_sequence — the number of the oldest reading still available. Anything below this has already been overwritten and cannot be requested.
  • next_sequence — the number the next reading will receive; equivalently, the total number of readings ever taken since boot.

Sequence numbers start at zero and increase by one for each reading, for the whole time the program runs. They never repeat and are never reused, which is exactly what makes a stateless "give me everything after N" request possible.

from — if the client requested a reading that has already been overwritten, the request is not refused; the starting point is moved forward to the oldest reading still held. The value used is reported back in the reply, so a client that was offline long enough for readings to be overwritten can compare the value it sent with the value returned and determine that those readings are no longer available.

available — how many readings exist from that point onwards. saturating_sub subtracts but stops at zero instead of wrapping around to a very large positive number. Without it, a client requesting a from beyond the newest reading would produce a count of billions and the device would attempt to send that many entries.

Unlike the other replies, this one does not state its length. The body is produced one reading at a time and its total size is not known when the headers are sent. HTTP/1.1 allows this when the reply states Connection: close: the end of the body is the end of the connection. The close-then-reset sequence in the calling loop is therefore what indicates to the browser that the body is complete.

The alternative would be to build the whole reply in memory first, which for 2000 readings would require permanently reserving over a hundred kilobytes of RAM that is unused between requests.

Including the buffer state here means a client can use a readings reply on its own, without a separate status request.

One 384-byte buffer is used for this text and reused for every reading that follows, so 384 bytes is the total buffer memory used by the whole reply.

One reading is fetched per iteration. The lock protecting the shared storage is taken and released inside that single call, so it is never held while data is being written to the network. A slow or stalled client therefore cannot delay the sensor tasks, which measure on a fixed schedule.

Each stored entry carries both the measured values and the uptime at which the measurement finished, reported as taken_at_ms.

For the SCD41, CO₂ is published exactly as the sensor reports it, in parts per million. The same handling for the particle sensor. Five values are published: the mass concentrations for particles up to 1.0, 2.5, 4.0 and 10 micrometres in micrograms per cubic metre, plus the typical particle size in micrometres.

The sensor's driver also measures particle counts for several size classes (nc0_5 through nc10). Those are stored but not published, because the page does not display them and omitting them shortens every reply.

Each formatted reading is written to the socket as soon as it is produced, so at most one formatted reading is held in memory at a time. If a write fails, because the browser navigated away or the connection dropped, the function returns immediately and the body it has sent is truncated and not valid JSON. No recovery is attempted: the client that would have parsed the body has already disconnected, and the calling loop resets the socket for the next client.

Finally ]} closes the array and the object. The connection being closed immediately afterwards, in the calling loop, is what indicates to the browser that the body is complete.

Failure behaviour

SituationBehaviour
No network name compiled in One message on the serial console; the Wi-Fi task ends. Sensors, LED and history all continue working. The device is not reachable over the network.
Wrong password, or router not present Association fails, the error is printed, and the attempt repeats every five seconds indefinitely.
Router reboots The disconnection event wakes the Wi-Fi task, which waits five seconds and rejoins automatically. No device reset is needed.
Associated but no IP address The server task waits before binding, so it never listens on an address it does not have. Nothing is printed until the address arrives.
Browser connects and then stops responding The ten-second inactivity timeout drops the connection and the socket is reset, freeing the server for the next client.
Browser closes mid-reply The write fails, the handler returns early, and the loop resets the socket. Nothing is retried and no state is left behind.
Measurement storage could not be reserved at startup Both histories report zero capacity and zero length. The endpoints still work and return empty data; the page shows no history.
A reading is overwritten while being sent That array position becomes null. The element count is unaffected, so the client's mapping from position to sequence number stays correct.
Client asks for readings that were overwritten The start point moves to the oldest available reading without an error, and the reply reports the value used in its from field.
Request headers exceed 512 bytes 431 is returned and the connection ends. No buffer can be overrun.
