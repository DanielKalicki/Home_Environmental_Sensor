What this file does

This one file contains everything the device needs to be reachable over your home network. It does three separate jobs, each running as its own independent task:

  1. Join the Wi-Fi network. The board behaves like a phone or laptop: it connects to an existing wireless router using a network name and password that were compiled into the firmware. It does not create its own hotspot.
  2. Run the network stack. The library that implements IP, TCP and DHCP only performs work while a task calls it, so one task exists to call it continuously.
  3. Answer HTTP requests. A server listens on TCP port 80 and replies to exactly three addresses, all of them read-only JSON.
No user interface is served. Earlier revisions of this firmware embedded an index.html page in the binary and served it from /. That is gone. The device now publishes data only, and the human-facing charts live in the separate SvelteKit application under frontend_server/, which polls these three endpoints and keeps its own copy of the history on disk. A request for / therefore returns 404 Not Found.

The file stores nothing itself. All the measured data lives in a separate module, utils/shared_state.rs, which the nine sensor tasks write into and this file only ever reads from. This file converts that stored data into HTTP responses.

Constraints that shaped the implementation

  • No memory is allocated while running. There is no heap allocator in this firmware, so every buffer used here is a fixed-size area reserved at compile time. That is why the two large responses are written out in small pieces instead of being assembled into one big string.
  • One client at a time. A single connection is accepted, answered, and closed before the next one is accepted. This keeps memory use to two 1536-byte buffers.
  • The device keeps no per-client state. It does not record which client has received which readings. Each reading has a number that never repeats, so a client requests "everything from number N onwards" and the device answers using only that number.
  • The device has no clock. There is no battery-backed real-time clock on the board, so readings are timestamped with "milliseconds since the board powered on". Every response also reports the current uptime, which lets the client convert those numbers into real dates using its own clock.
  • Every wait is bounded. This task is the only caller of accept, so a single wait that never finishes would make the device permanently unreachable on port 80 while still answering the network in every other respect. Both waits in the teardown sequence are therefore capped by CLOSE_TIMEOUT_MS.

Two guarantees about this reply. First, the array always contains exactly count elements, so the element at position i is always the reading numbered from + i, including when some positions are null. Second, a from value naming a reading that has already been overwritten is moved forward to the oldest retained reading without returning an error, and the value actually used is reported in the from field, so the client can determine that some readings were not received.

Two conversions happen at the moment a reading is written into the reply rather than when it is stored. The SCD41's temperature and humidity are held as raw 16-bit sensor words and converted by temperature_celsius() and humidity_percent(); the same is true of the SHT41, the BMP581 and the OPT4048's derived colour values. Storing the raw form keeps each retained reading smaller, and thousands of them are retained.

The BME690's temperature_celsius and humidity_percent are BSEC's heat-compensated values, with the sensor's own heating element removed from the figure. The raw_ pair is what the sensor itself reported. The BMM350's temperature is its own die, which runs warmer than the room, which is why it is named die_temperature_celsius and not grouped with the others.

"Station" means the radio acts as a client of an existing router, the same way a laptop does. The alternative, not used here, would be access-point mode, where the board itself broadcasts a network for others to join.

The word chosen is API, not server page: what this file exposes is machine-readable data, not something a person looks at directly.

//! The board joins an existing Wi-Fi network as a client (station mode) and
//! answers JSON requests on TCP port 80. No user interface is served: the
//! device publishes data only, and a separate frontend server reads it. Three
//! tasks cooperate:
//!
//! * `wifi_connection_task` keeps the radio associated with the access point.
//! * `net_task` runs the embassy-net TCP/IP stack.
//! * `web_server_task` accepts connections and answers HTTP requests.
//!

"Port 80" is the default port for unencrypted web traffic, which is why the device address can be typed without a port number after it.

"No user interface is served" is the design decision that separates this firmware from a typical hobby web server. Rendering charts needs fonts, layout and JavaScript, all of which would have to be stored in the board's flash and sent over a slow link on every visit. Instead the board sends only numbers, and frontend_server/ — an ordinary computer running SvelteKit — does the drawing.

The three tasks are separated because each has a different reason to wait. The Wi-Fi task waits on radio events, the network task waits on packets, and the server task waits on connections. Combining them would mean one of those waits blocking the other two.

//! Two resources are served, both of them read-only:
//!
//! * `GET /api/status` returns the device uptime and the state of every
//!   history.
//! * `GET /api/readings` returns one page of a single sensor's readings.
//! * `GET /api/thermal` returns the newest thermal image.
//!

The three endpoints, and the guarantee that none of them changes anything on the device. There is no request that writes, configures, calibrates or resets.

This comment contradicts itself. It says "Two resources" and then lists three. The thermal endpoint was added later and the sentence above it was not updated. The list is correct; the count is not. Nothing depends on the comment, so the behaviour is unaffected — but the sentence should read "Three resources".
//! A client fetches the retained history once, a page at a time, and
//! afterwards asks only for the readings taken since the last one it holds.
//! `README.md` documents both endpoints in full.

The intended usage pattern, and the reason the API is shaped around sequence numbers rather than timestamps. A client that has been running for a week does not re-download a day of readings on every poll; it asks for what came after the last number it received.

This works without the device remembering anything about that client. All the state lives in the request: "give me everything from N". That is what makes a single socket enough.

/// Longest wait for a finished connection to drain before it is discarded.
///
/// Only the orderly case is worth waiting for. A client that walked away
/// mid-response leaves part of that response in the transmit buffer, and that
/// buffer is never drained: it is emptied when the socket is listened on
/// again, not when the connection ends. Waiting for it unconditionally would
/// therefore be a wait that never ends.
const CLOSE_TIMEOUT_MS: u64 = 2000;
Prevents a permanent hang

Two seconds. This constant exists because of a specific failure that has no obvious symptom: the device keeps answering pings, keeps measuring, keeps logging to serial — and silently refuses every connection to port 80 until it is reset.

The mechanism, spelled out in the comment: flush finishes when everything in the transmit buffer has been sent and acknowledged. If the client disappeared while a response was still being written, the bytes left in that buffer will never be acknowledged, because there is nobody left to acknowledge them. Closing the socket does not throw them away. So an unbounded flush at that point waits for an event that cannot happen.

That would park the server task forever, and this task is the only caller of accept — so no future connection would ever be picked up.

Abandoning the wait costs nothing: the next accept listens on the socket again, which resets it and discards whatever was still queued.

2,560 bytes, against a worst case of roughly 1,500. The status body is the one response that is built whole before any of it is sent, because it is the only one that carries a Content-Length — and the length cannot be stated until the text exists.

The margin is not caution for its own sake. A heapless::String that runs out of room does not panic and does not truncate loudly: it returns an error, and every caller here discards that error with let _ =. Connection buffers lines 86–89

/// Receive buffer for one client connection.
static mut RX_BUFFER: [u8; 1536] = [0; 1536];
Memory

A fixed 1536-byte area reserved for the entire life of the program. TCP needs somewhere to hold bytes that have arrived but have not yet been read by the application; this is that place.

1536 is chosen to be slightly more than the 1500-byte maximum size of a single Ethernet or Wi-Fi packet, so a full packet always fits without being split.

static mut means "one single global, changeable copy". Rust treats globals that can change as dangerous, because two tasks touching one at the same time would corrupt it. That is why the code that picks it up further below has to be explicitly marked as unchecked, together with a written justification.

/// Transmit buffer for one client connection.
static mut TX_BUFFER: [u8; 1536] = [0; 1536];

The matching buffer for the other direction: bytes that have been written by the application but not yet acknowledged by the peer.

This is the buffer CLOSE_TIMEOUT_MS exists for. When a client vanishes mid-response, what is left stranded is stranded here, and nothing will ever acknowledge it.

These two arrays are the entire memory cost of the HTTP server. It does not grow with the number of clients served, because the same pair is reused for every connection.

  • the first bounded flush() waits up to two seconds for the remaining bytes to actually leave and be acknowledged.

The five numbers come from shared_state.rs and describe a ring buffer — storage of fixed size where, once full, each new reading overwrites the oldest:

  • interval_ms — how often this sensor is scheduled to measure. It differs per sensor, so a client can tell a genuine gap in the data apart from the normal spacing between points.
  • capacity — how many readings fit. Zero means the storage could not be reserved at startup and nothing is being retained for that sensor; this is the field to check first when a history is unexpectedly empty.
  • len — how many are held right now.
  • first_sequence — the number of the oldest reading still available. Anything below this has already been overwritten and can never be requested again.
  • next_sequence — the number the next reading will receive; equivalently, the total number of readings taken since boot.

Sequence numbers start at zero and increase by one per reading for the whole time the program runs. They never repeat and are never reused, which is exactly what makes a stateless "give me everything after N" request possible without the device having to remember anything about the client.

The reason the camera is the one sensor without a history. A single frame is 24 rows of 32 pixels, 768 f32 values, 3,072 bytes. Retaining a day of those at the camera's frame rate would need more memory than the whole PSRAM budget, so exactly one image is kept and overwritten in place.

That makes sequence necessary. Because the reply always carries "the current image", a client polling the endpoint has no way to tell a fresh image from a repeat except by comparing pixel arrays. sequence is a counter incremented by the camera task each time it stores a new frame, so one integer comparison answers the question.

There is no from or limit here: with a single image there is nothing to page through.

The wire format. pixels is one flat JSON array of 768 numbers, not an array of rows; a client rebuilds the grid by cutting it every width entries. The first entry is the top-left pixel.

Two independent reasons are given for streaming row by row, and both matter:

  • Memory. 768 numbers printed to two decimals is roughly 5 kB of text. No buffer of that size exists in this firmware, so the body could never be assembled before sending.
  • Lock hold time. The image lives behind a mutex shared with the camera task. If this function copied the whole frame at once it would hold that mutex across a copy of 3 kB; instead it takes and releases the lock 24 times, once per row, so the camera task can store its next frame between rows.

The consequence of the second point is that a reply can mix rows from two different images if a new frame arrives mid-transfer. That is accepted deliberately: a torn thermal image is a cosmetic artefact, whereas blocking the camera task is a real stall.
