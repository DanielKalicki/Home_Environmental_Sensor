src/tasks/sps30_task.rs — periodic particulate-matter measurement

This task starts the SPS30 particle sensor’s continuous measurement mode, polls for a fresh sample, then reads and validates ten values every five seconds. It shares I²C0 with the eight other sensor tasks and releases the bus between polls, discards the first six readings while the fan and laser settle, saves every later result in external-memory history, and safely reinitialises after an error.

What this file does

The Sensirion SPS30 measures airborne particulate matter continuously after it receives a start command. This task starts that mode after boot or recovery, then takes one reading every five seconds. Before each reading, it asks the sensor up to thirty times whether fresh data is ready. Each poll is separated by 100 ms and releases the shared I²C bus while waiting.

A complete sensor result contains ten floating-point values: four mass concentrations, five particle-number concentrations, and a typical particle size. The task prints all ten values to the USB serial console. It stores the complete result in history, although the web server publishes only the four mass concentrations and the typical particle size.

The SPS30 produces new values about once per second, while this task samples every five seconds. The task does not try to retrieve the values produced between its scheduled reads; it records the most recently available result at each read.
DISCARDED_WARMUP_READINGS is 6. The first six readings after every initialisation — at boot and after each recovery, so roughly the first thirty seconds — are printed with a (warm-up, discarded) marker and kept out of the history, because the fan and laser need tens of seconds of continuous operation before the optical measurement settles.
An exhausted readiness-poll window is deliberately not an error: the task reads the sensor’s latest values anyway. Only a failed transfer or a bad CRC enters recovery.

Every component this task depends on

ComponentInput → operation → output
SharedI2cBusOwns I²C0, SDA GPIO5, and SCL GPIO6. A mutex gives one sensor task exclusive access. Before every transfer, acquire() restores the bus to idle and builds a new 100 kHz blocking I²C controller.

Startup code creates the bus, reserves history, and starts this task once, alongside the eight other sensor tasks that share the same bus. This task does not configure GPIO pins, map PSRAM, or create a network service.

/// Time between scheduled read-out deadlines.
pub const MEASUREMENT_INTERVAL_MS: u64 = 5000;
Schedule

Five seconds, and the only pub item in this group. It is public because shared_state imports it to size the history: SPS30_CAPACITY = HISTORY_WINDOW_MS / MEASUREMENT_INTERVAL_MS = 86,400,000 / 5,000 = 17,280 entries for one day.

“Scheduled read-out deadlines”, not “time between readings”: the sensor produces a new result about once per second regardless. This task deliberately samples one in five and ignores the rest.

One second, used on both failure paths — a failed initialisation and a failed read. Private, because nothing outside this file needs it.

Its purpose is to stop a missing sensor from spinning the loop at full speed and monopolising the bus. One second is short enough that a sensor plugged in later is picked up almost immediately.

/// How many readings are dropped after the measurement is started.
///
/// The fan and laser need tens of seconds of continuous operation before the
/// optical measurement settles, so the readings taken right after the start
/// command are not representative; at the interval above, six of them cover
/// roughly the first half minute. Discarded readings are still read and
/// printed, they are only kept out of the published history, so the settling
/// period cannot distort the charts. The count restarts after every
/// re-initialisation, including the one following a bus error. Set to 0 to
/// publish every reading.
const DISCARDED_WARMUP_READINGS: u32 = 6;
Warm-up discard

Ten lines of comment for one line of code, because the number is a judgement rather than a datasheet figure and the reasoning cannot be recovered from the value.

Why the SPS30 needs six and the SCD41 needs one. This sensor draws air past a laser with a fan. Both must reach a steady state before the optical count means anything, which takes tens of seconds — far longer than the SCD41’s single settling conversion. Six readings at five seconds each cover about thirty seconds.

Discarded is not the same as unread. The readings are still fetched and still printed, with a marker; only their entry into the published history is withheld. A silent console therefore always means a broken sensor, never a suppressed one.

The comment states two operational facts a reader would otherwise have to derive: the count restarts after every initialisation including error recovery, and setting it to 0 disables the mechanism cleanly.

Thirty attempts. The type is usize rather than u64 because this value is used as the upper bound of a for range, not as a millisecond count.

const DATA_READY_POLL_DELAY_MS: u64 = 100;
Poll spacing

100 ms between attempts. Together with the constant above this gives a polling window of 30 × 100 ms = 3 seconds, which fits inside the five-second interval with time to spare for the read itself.

The spacing is set against the sensor’s roughly one-second result rate: a fresh result is normally flagged within the first ten or so polls, so the full window is only ever consumed when something is wrong.

Deliberately ignored result

Sends command 0x0104 and waits 20 ms. let _ = discards the Result and, just as importantly, silences the must_use warning that would otherwise appear — the discard is explicit and reviewable rather than accidental.

The result must be ignored, because both outcomes are acceptable. If the sensor was measuring (a soft reset of the microcontroller alone leaves it running), the stop succeeds and is needed. If it was already idle, it may reject the command — and that rejection is not a fault.

Without this line, a firmware restart without a power cycle would leave the sensor measuring, the following start command would be rejected, and the task would loop in recovery forever against perfectly healthy hardware.

Start command

Sends command 0x0010 with the CRC-protected argument 0x0300, which selects big-endian IEEE-754 float output, then waits 20 ms. The fan and laser start here and run continuously until stopped.

This is the structural difference from the SCD41 task. There, every reading is started by its own command. Here one command starts a continuous mode that keeps producing results on its own, and the read-out loop merely samples it.

Driver, controller and lock guard are dropped here in reverse order of creation. The bus was held for three exchanges plus two 20 ms command delays — well under a tenth of a second — and is free again before the caller does anything else.

read_once — poll for freshness, then read lines 64–87

/// Wait for the sensor to flag a fresh result, then read it.
///
/// If no flag appears within the poll window the last values are read anyway;
/// a genuine bus problem still surfaces as an error from the read itself.
Documentation comment

The second paragraph documents the single most surprising decision in the file: exhausting the poll window is not treated as an error.

The reasoning is that the flag is an optimisation, not a safety check. The sensor holds its most recent values whether or not it has flagged them as new, so reading anyway yields data that is at worst slightly stale. Treating a missing flag as a failure would instead throw away a working sensor's output and force a pointless re-initialisation.

Nothing is hidden by this: a real fault still produces a bus or CRC error from the read on the next line, which is reported.

Waits until the next five-second deadline, not for a further five seconds. Three actions, in this order. Setting needs_init makes the next pass re-run the serial-number check and the start command, because after a failed exchange the sensor's mode is unknown — it may have been reset and stopped measuring. The message prints the error variant, Bus(…) or Crc, which distinguishes a wiring or acknowledgement problem from corrupted data on an otherwise working link.

The one-second wait replaces ticker.next(): the ticker is deliberately not advanced here, and its stale deadline is dealt with by the reset() after the next successful read. Nothing is published, so a failure leaves a visible gap in the history rather than a fabricated value.

Note this arm is reached by a genuine bus or CRC error only. An exhausted poll window never gets here.

        }
    }
}
Closing braces

In order: the match, the loop, and the function. The last is unreachable — the loop has no exit — but the compiler requires it, and it is what gives the function its () return type in the eyes of the #[embassy_executor::task] macro.

Dependent component: the SPS30 driver

The driver is an allocation-free object containing only a borrowed I²C controller and the fixed SPS30 seven-bit address, 0x69. It sends commands as big-endian 16-bit values. Returned two-byte words are followed by CRC-8 bytes using polynomial 0x31, initial value 0xFF, no reflection, and no final XOR.

start_measurement()Sends 0x0010 (start_measurement) plus format argument 0x0300, then waits 20 ms.

Each command-and-response read is intentionally two separate I²C transactions, not a repeated-start combined write/read, because that is what the SPS30 protocol requires.

Complete I²C, shared-state, history, and PSRAM dependencies

Shared I²C0

I2cBus owns i2c0: I2C0, sda: SdaPin, scl: SclPin, clocks: &'static Clocks<'static>, and delay: Delay. SdaPin = GpioPin<I2C_SDA_PIN> and SclPin = GpioPin<I2C_SCL_PIN>, where I2C_SDA_PIN = 5 and I2C_SCL_PIN = 6. SharedI2cBus = Mutex<CriticalSectionRawMutex, I2cBus>. Its acquire() calls recover_i2c_bus(), then creates a controller at I2C_FREQUENCY_KHZ = 100. Recovery configures open-drain pins, pulses SCL nine times at five-microsecond half periods, and produces STOP by releasing SDA high while SCL is high.

Shared state and history

shared_state::init(psram) reserves SPS30_CAPACITY = 17,280 optional samples for one day, because HISTORY_WINDOW_MS = 86,400,000 and this task’s interval is 5,000 ms. It reserves one slice per sensor history — eight in total, for the SPS30, SCD41, BME690, AS7343, BMP581, OPT4048, SHT41 and BMM350 — each sized by the same HISTORY_WINDOW_MS / interval formula using that task’s own MEASUREMENT_INTERVAL_MS. Sample<T> contains value and taken_at: Instant. HistoryStatus contains interval_ms, capacity, len, first_sequence, and next_sequence.

publish_sps30() briefly locks shared state and pushes Sample { value: measurement, taken_at: Instant::now() } when the history exists. publish_scd41() through publish_bmm350() are the corresponding operations for the seven other sensors, and all eight share one state mutex. sps30_status() and its seven counterparts copy their status. sps30_reading(sequence) and its seven counterparts copy one retained sample or return None.

MeasurementHistory<T> stores the permanent entry slice plus next, len, and pushed. new() rejects empty storage; push() writes, wraps the index, caps length, and increments pushed. capacity(), len(), first_sequence(), next_sequence(), get(), and private get_oldest() provide the exact ring-buffer interface. The sequence formula is first_sequence = pushed − len; it advances when a full buffer overwrites its oldest entry.

PSRAM

Psram::init() maps external PSRAM before tasks start. free_bytes() returns remaining mapped capacity. alloc_slice<T>(len, value) aligns the next address, checks arithmetic and bounds, fills all elements, advances the permanent allocation pointer, and returns a permanent mutable slice; it returns None when the request does not fit. If history allocation fails, every publish_* function drops readings while sensor measurement and serial output continue.

Complete I²C startup scan interface

Although the SPS30 task does not call it after startup, the same I2cBus dependency also provides scan(). Firmware calls it before the bus enters SharedI2cBus. scan() calls public scan_i2c(), which probes every address from I2C_FIRST_ADDRESS = 0x03 through I2C_LAST_ADDRESS = 0x77.

I2C_ADDRESS_COUNT and MAX_I2C_DEVICES both represent the number of addresses in that inclusive range. Every probe uses an empty address-only write, so it does not select a device register. Each address gets I2C_SCAN_RETRIES = 3 attempts, separated by I2C_SCAN_RETRY_DELAY_MS = 10 ms; recovery and controller reconstruction happen before every attempt. print_scan_progress() displays a SCAN_PROGRESS_BAR_WIDTH = 30-character serial progress bar using # for completed segments and . for remaining segments.

I2cScanResult stores addresses: [u8; MAX_I2C_DEVICES] and count: usize. Its addresses() method returns the used prefix as &[u8]. Public print_scan_result() prints each returned address or prints that no I²C device acknowledged.

MeasurementHistory<T> stores next: usize, len: usize, and pushed: u64 in addition to its permanent entry slice. These exact types allow the ring buffer to use an array index for current position and length while retaining a non-repeating 64-bit sequence count for its entire uptime.

Failure behaviour

SituationTask behaviour
Sensor absent or I²C transfer failsPrints the error, marks the sensor as needing initialisation, waits one second, recovers I²C0, and retries the serial-number and start sequence.
Returned word has an invalid CRCThe driver returns Crc; the task prints a measurement failure and performs the same reinitialisation path.
Fresh-data flag stays falseAfter 30 checks, reads the latest available result anyway. This alone does not enter recovery, and the reading is stored and printed like any other.
Another sensor task currently uses I²C0Waits for the shared mutex. Transfers cannot overlap. The mutex is released between SPS30 readiness polls and during every timer wait.
Sensor already measuring during recoveryThe task attempts stop_measurement() before start_measurement() and ignores its result, so the start command is issued from the expected idle state. Without this, a firmware restart without a power cycle would loop in recovery against healthy hardware.
First six readings after boot or after any recoveryPrinted with a (warm-up, discarded) marker and not stored. The counter is reset to 6 by every successful initialisation, so about thirty seconds of settling is dropped per recovery, not only at boot.
Serial number is not valid UTF-8<non-ascii> is printed in its place and initialisation continues. The text is never parsed, so a garbled serial cannot stop measurement — and unwrap_or avoids a panic that would halt the whole device.
Sensor fails, then recovers minutes laterThe history contains a gap for the outage; no values are interpolated or repeated. After the first successful read the ticker is reset, so the missed deadlines do not produce a burst of back-to-back reads.
History storage is unavailableMeasurement and console output continue; only retention and web-history output are absent.
