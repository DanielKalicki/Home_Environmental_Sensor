What is this file?

main.rs is the starting point of this program. When the microcontroller (a small chip called the XIAO ESP32‑S3) powers on, this is the very first piece of Rust code that runs. This particular program has no operating system underneath it — it talks to the hardware directly — so it looks a little different from a normal "desktop" Rust program. A few ideas that are unique to this style of programming are explained the first time they appear, and every concept used in the file is also collected in the glossary at the bottom of the page.

A quick vocabulary check before we start:

  • Crate: a package of Rust code, similar to a "library". Names like embassy_executor or esp_hal are crates written by other people that this project depends on (listed in a file called Cargo.toml).
  • Function: a named, reusable block of code that performs a task. You "call" it by writing its name followed by parentheses, e.g. take().
  • Variable: a name that refers to a value stored in memory, created with the let keyword.
  • Statement: one instruction. In Rust, most statements end with a semicolon ;, exactly like a full stop ends a sentence.

#![no_std]
New concept · Attribute

This is an attribute — an instruction to the compiler that isn't part of the program's normal logic, it just changes how the compiler treats the code. You can always recognise one by the #[ ] or #![ ] brackets.

The ! right after # means this attribute applies to the whole file (and everything in it), rather than just the one line below it.

no_std tells Rust: "don't use the Standard Library". Normally Rust programs can use a large built-in toolbox called std that assumes you have an operating system underneath you (for files, networking, threads, etc.). This program runs directly on a small chip with no operating system, so that toolbox isn't available — only a much smaller core set of features (called core) can be used instead.

Learn more about attributes, in general

An attribute is metadata attached to a piece of code that instructs the compiler to do something extra with it. They show up constantly in ordinary (non-embedded) Rust too, for things like automatically generating code, marking test functions, or silencing specific warnings.

Common attributes you'll see in everyday Rust

#[derive(Debug, Clone)]      // auto-generate trait implementations
struct Point { x: i32, y: i32 }

#[test]                       // marks this function as a unit test
fn it_adds_up() {
    assert_eq!(2 + 2, 4);
}

#[allow(dead_code)]           // silences the "never used" warning
fn unused_helper() {}

#![allow(unused_imports)]     // inner attribute: applies to the whole file

#[derive(Debug, Clone)] is especially common: instead of you writing the code to print a struct or duplicate it by hand, that attribute tells the compiler to generate that code for you automatically, based on the struct's fields.

#![no_main]

Another whole-file attribute. Normally, Rust automatically generates some hidden startup code that eventually calls your main function the way a desktop operating system expects. On this chip there is no such operating system convention to follow, so no_main tells the compiler "don't generate that hidden startup code — the entry point will be provided a different way" (you'll see how, further down, at line 31‑32).

use embassy_executor::Spawner;
New concept · Import (use)

The use keyword imports a name so the rest of the file can refer to it directly. Without this line, you would have to write the full path embassy_executor::Spawner everywhere instead of just Spawner.

Spawner is a type (shown in blue) provided by the embassy_executor crate. It's the tool this program later uses to start background tasks (see lines 68‑70).

Learn more about use and imports, in general

use only creates a shortcut to a path — it doesn't copy or include any extra code. You can rename what you import, pull in several items at once, or re-export something so other code that imports your module gets it too.

use std::collections::HashMap;
use std::io::{self, Read, Write};       // import several items from one module
use std::fmt::Result as FmtResult;      // rename on import with `as`

pub use crate::shapes::Circle;          // re-export: others can `use your_crate::Circle`

Without any use line at all, you could still use something by writing its entire path every time, e.g. std::collections::HashMap::new() — use just saves you from repeating that.

use esp_println::println;
New concept · Macro

Imports println from the esp_println crate. You'll see it used with a trailing ! as println!(...) — that trailing ! marks it as a macro, not an ordinary function.

A macro is code that generates more code at compile time (before the program even runs), which is how println! is able to accept a flexible, printf-style format string plus any number of extra values. This particular version prints text out over the chip's debug serial connection, since there's no regular screen or terminal attached (the normal std library's println! isn't available here, because of #![no_std]).

Learn more about macros, in general

A macro is always recognisable by its trailing !. Unlike a regular function, a macro runs at compile time and generates Rust code, which is how it can accept a flexible, variable number of arguments and even different argument types in different places — something an ordinary function's fixed signature can't do.

A simple macro you can define yourself

macro_rules! square {
    ($x:expr) => { $x * $x };
}

fn main() {
    println!("{}", square!(5)); // this line expands to: 5 * 5
    let v = vec![1, 2, 3];      // vec! is a standard-library macro too
}

Some other very common macros: vec![...] (build a growable list), format!(...) (build a String instead of printing it), and assert_eq!(...) (used heavily in tests).

mod drivers;
New concept · Module

Declares that this project has a module named drivers. A module is a named grouping of code used to keep a project organised into logical pieces, similar to a folder. This line tells the compiler "go look for a file called drivers.rs or a folder drivers/ with a mod.rs inside it, and treat its contents as part of this project under the name drivers". Learn more about modules, in general

Modules can be nested inside each other, forming a tree, and every item (function, struct, etc.) is private to its module by default — you have to mark it pub to let code outside the module use it.

// src/main.rs
mod shapes; // looks for src/shapes.rs (or src/shapes/mod.rs)

fn main() {
    let c = shapes::Circle::new(2.0);
}

// src/shapes.rs
pub struct Circle { pub radius: f64 }

impl Circle {
    pub fn new(radius: f64) -> Self { Circle { radius } }
}

If pub were removed from struct Circle or new, main.rs would fail to compile with a "private" error — this is Rust's way of letting a module hide its internal details.

static TIMERS: StaticCell<[OneShotTimer<ErasedTimer>; 1]> = StaticCell::new();
New concept · Static variable New concept · Generics

static creates a value that lives at one fixed place in memory for the entire time the program runs, as opposed to a normal let variable which only exists while its surrounding function is running. TIMERS is the name of this static value.

After the colon : comes its type: StaticCell<[OneShotTimer<ErasedTimer>; 1]>. The angle brackets < > are generics — they mean "this type is a container/wrapper around another type, and here is which one". So this reads as: "a StaticCell that holds a [OneShotTimer<ErasedTimer>; 1]". The square brackets [Type; 1] mean a fixed-size array holding exactly 1 item of that type.

Finally, = StaticCell::new(); creates an empty/uninitialised StaticCell right now (at compile time), ready to be filled in with the real value later while the program is running (that happens at line 40).

Learn more about static variables, in general

const and static look similar but differ: a const is copied/inlined everywhere it's used and has no fixed address; a static lives at exactly one fixed memory address for the whole program. A plain static must be immutable unless wrapped in something designed for safe shared mutation, like an atomic type or (as in this file) a StaticCell/Mutex.

static GREETING: &str = "hello"; // fixed at compile time, never changes
const MAX_USERS: u32 = 100;      // inlined wherever it's used

use std::sync::atomic::{AtomicU32, Ordering};
static COUNTER: AtomicU32 = AtomicU32::new(0); // safely mutable static

fn increment() {
    COUNTER.fetch_add(1, Ordering::SeqCst);
}
Learn more about generics, in general

Generics let one function, struct, or enum work with many different types instead of writing a separate copy for each one. The compiler generates a specialised version for every concrete type actually used (called "monomorphization"), so there's no extra cost while the program runs.

fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list[0];
    for &item in list {
        if item > largest { largest = item; }
    }
    largest
}

struct Wrapper<T> { value: T }

let a = largest(&[3, 7, 2]);       // T becomes i32 here
let b = largest(&[3.1, 7.5, 2.2]); // T becomes f64 here

T: PartialOrd + Copy is a "trait bound" — it restricts T to only types that support comparison and copying, so the function body is allowed to use > on them.

static CLOCKS: StaticCell<Clocks<'static>> = StaticCell::new();
New concept · Lifetime

Same pattern as line 25: an empty StaticCell that will later hold a Clocks<'static> value (filled in at line 35).

The new piece here is 'static — a lifetime. A reference (a value that points at data owned somewhere else, written &T — explained in full at line 62) is only allowed to be used for as long as the data it points to is still alive. Since Rust has no garbage collector, the compiler needs some way to check this at compile time instead of at runtime. A lifetime is simply a name for one such "how long is this guaranteed to stay valid?" question, so the compiler can check whether everything lines up. 'static is one specific, named answer to that question: "valid for the entire rest of the program — it will never be cleaned up early". You'll always recognise a lifetime by its leading apostrophe, e.g. 'static, 'a.

Learn more about lifetimes, in general

The problem lifetimes exist to prevent

Imagine this function were allowed to compile:

fn dangling() -> &String {
    let s = String::from("hi"); // `s` is created inside this function
    &s
} // `s` is destroyed right here, the moment the function ends —
  // so the reference we tried to return would point at memory
  // that no longer holds anything. Rust refuses to compile this.

This is called a dangling reference: a reference that outlives the data it points to. In languages like C, this compiles fine and can crash your program, or silently read garbage, at runtime. Rust's compiler instead checks, for every single reference in your code, "can I prove the data behind this is still alive for as long as this reference might be used?" — and simply refuses to compile the program if it can't prove that. A lifetime is the name it gives to that "still alive for this long" guarantee while it's doing that check.

Why you sometimes have to write one yourself

Most of the time the compiler works this out silently and you never write a lifetime at all. You only need to write one explicitly when a function's signature is ambiguous about which input a returned reference is tied to — most commonly, when a function takes more than one reference as input and returns a reference too:

// Without a lifetime, this line alone doesn't say which of x or y
// the returned reference is allowed to be tied to — so the compiler
// requires you to spell it out:
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

let result;
{
    let a = String::from("hello");
    let b = String::from("hi");
    result = longest(&a, &b); // borrows from both `a` and `b`
    println!("{result}");     // fine: `a` and `b` are still alive here
}
// using `result` down here would be a compile error: it might be
// borrowed from `a` or `b`, and both have already been destroyed.

Writing <'a> and reusing 'a on x, y, and the return type doesn't make anything live longer. It's a promise you make to the compiler: "the reference I return will never be valid for longer than the shorter-lived of x and y". The compiler then checks every place that calls longest against that promise.

The 'static special case

'static is the one named lifetime built into the language, meaning "valid for the entire program, guaranteed to never be cleaned up early" — so it satisfies any lifetime requirement, no matter how long. A plain string literal like "hello" is always 'static, for example, because its text is baked directly into the compiled program and exists for as long as the program runs. That's exactly why it's used in this file: the values stored in CLOCKS, TIMERS, and BUS need to be safely usable by every task for as long as the program runs, so their type says 'static up front instead of asking the compiler to work out some shorter, more limited guarantee.

32
async fn main(spawner: Spawner) {
New concept · async function

fn main( ... ) { ... } declares a function named main — the program's entry point. Everything between this line's opening curly brace { and the matching closing brace on line 71 is the body of this function, run in order from top to bottom.

async marks it as an asynchronous function. A normal function that has to "wait" for something (like a sensor to respond, or a timer to elapse) would freeze the entire processor while waiting. An async function is instead able to pause itself at a waiting point and let other tasks use the processor in the meantime, then resume later when the thing it was waiting for is ready. This is essential here because the program runs several tasks side-by-side (blinking an LED, reading two different sensors) on a single small chip.

(spawner: Spawner) is the function's single parameter: a variable named spawner, of type Spawner (imported on line 4). It's handed to main automatically by the attribute on line 31, and it's the tool used later (lines 68‑70) to start the background tasks.

Learn more about async functions, in general

Calling an async fn does not run its body immediately — it produces a value called a Future, which is an inert description of work to be done later. Nothing happens until that future is either .awaited inside another async function, or handed to a runtime/executor (like tokio, async-std, or embassy in this project) that knows how to actually run it and switch between many futures while they wait.

async fn fetch_temperature() -> f32 {
    // pretend this pauses while waiting on real input/output
    42.0
}

#[tokio::main] // a common general-purpose async runtime outside embedded code
async fn main() {
    let t = fetch_temperature().await; // pauses here until the value is ready
    println!("{t}");
}

Forgetting the .await is a classic beginner mistake — the future is created but never actually run, so nothing happens (the compiler warns about this).

33
    let peripherals = Peripherals::take();
New concept · let / variables

let creates a new variable. Here, a variable named peripherals is created and set equal to whatever is on the right of the = sign. By default, variables created with let are immutable — once set, their value cannot be changed again (see line 47 for the opposite, mutable case).

Peripherals::take() calls the take associated function on the Peripherals type (an associated function is a function that belongs to a type but isn't called on a specific value of it — recognisable by the :: double-colon instead of a dot). It hands over exclusive access to every piece of hardware built into the chip, exactly once — calling it twice would be an error, which guarantees no two parts of the program can ever fight over the same piece of hardware.

Learn more about let and variables, in general

let can also destructure a value into several variables at once, and the type is usually left out because Rust infers it from the value on the right — you only write the type explicitly when you want to be clear, or when there's genuinely no way to infer it.

let age = 30;              // immutable, type inferred as i32
let name: &str = "Ada";    // type written out explicitly
let (a, b) = (1, 2);       // destructuring: a = 1, b = 2

let age = age + 1; // allowed: this shadows the earlier `age` with a new one

New concept · Struct fields

peripherals.SYSTEM uses the dot . to reach into the peripherals value and pull out its SYSTEM field — one specific piece of hardware (the system-control registers) out of the whole bundle taken on line 33.

SystemControl::new(...) calls the new associated function to build a fresh SystemControl value out of that piece of hardware, and it's stored in a new variable named system. Learn more about structs, fields, and constructors, in general

A struct groups related values into one named type; dot notation reaches into a specific value's fields. An "associated function" (called with Type::name(...), no dot) is different from a "method" (called with value.name(...), takes self as its first parameter).

struct Rectangle { width: u32, height: u32 }

impl Rectangle {
    fn new(width: u32, height: u32) -> Self { // associated function, no `self`
        Rectangle { width, height }
    }
    fn area(&self) -> u32 { // method, takes &self
        self.width * self.height
    }
}

let r = Rectangle::new(10, 5); // called with `::`, it's a constructor
let a = r.area();              // called with `.`, it's a method on `r`
35
    let clocks = CLOCKS.init(ClockControl::max(system.clock_control).freeze());
New concept · Method chaining

This line does several things, evaluated from the inside out:

1) system.clock_control reads a field out of the system value from line 34.

2) ClockControl::max(...) calls an associated function that starts building a clock configuration set to the fastest available speed.

3) .freeze() is a method call — a function called with dot-syntax directly on a value (here, on the result of step 2). It locks in that configuration and produces the final, ready-to-use Clocks value. Chaining method calls with dots like this (a().b().c()) is a very common Rust style, read left to right as "do this, then do this to the result, then do this to that result".

4) CLOCKS.init(...) takes that finished Clocks value and stores it inside the CLOCKS static from line 27 — this is the moment that "empty box" actually gets filled in, for the one and only time. It hands back a reference to the value that is now guaranteed to live for the rest of the program, which is saved into the new variable clocks.

Learn more about method chaining, in general

This style is sometimes called the "builder pattern": each method takes the value produced by the previous one and returns a new (or the same, transformed) value, so a whole sequence of operations can be read left to right as one flowing sentence instead of deeply nested function calls.

let msg = String::from("  Hello, World!  ")
    .trim()            // -> &str, removes leading/trailing whitespace
    .to_lowercase()     // -> String, all lowercase
    .replace("hello", "hi");

println!("{msg}"); // prints: hi, world!

Compare that to the nested, harder-to-read equivalent: String::from(...).replace(...).to_lowercase()... written inside-out — chaining with dots avoids that by reading top-to-bottom, one step at a time.

New concept · Type conversion

timg0.timer0 reads the first individual timer out of the timer group. The : ErasedTimer after the variable name is an explicit type annotation — normally Rust can figure out a variable's type automatically, but writing it explicitly here tells the compiler exactly which type to convert into.

.into() is a conversion method: it turns a value of one type into a different (but compatible) type. Here it converts the specific hardware timer type into the more general ErasedTimer type, so that other code (like the embassy task runner) doesn't need to care exactly which hardware timer is behind it.

Learn more about type conversion, in general

.into() relies on the standard library's From /Into traits: if someone has written "you can build a B From an A", then every A automatically gets a matching .into() to become a B. This is different from as, which does a raw, low-level cast (e.g. between number types) and can silently lose information.

struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self {
        Fahrenheit(c.0 * 9.0 / 5.0 + 32.0)
    }
}

let c = Celsius(100.0);
let f: Fahrenheit = c.into(); // uses the From implementation above

let n: u8 = 300i32 as u8; // "as" truncates: n ends up being 44 (300 % 256)

Learn more about mutability, in general

mut also appears on references, as &mut T ("an exclusive, writable borrow"). Rust's compiler enforces a strict rule: for any given value, you may have either one &mut reference, or any number of plain & (read-only) references — never both at the same time. This single rule is what prevents data races at compile time, without needing a garbage collector or manual locks in ordinary single-threaded code.

let mut count = 0;
count += 1; // OK, `count` was declared mutable

fn increment(n: &mut i32) {
    *n += 1;
}

let mut x = 5;
increment(&mut x);

About that *n += 1; line specifically: inside increment, the parameter n is not the number itself — its type is &mut i32, a reference, meaning n only holds the location where some i32 is stored elsewhere (in this case, back in x). If you wrote plain n += 1, you would be trying to add 1 to that location/address, which is not a number and makes no sense. Writing *n instead means "don't use the reference itself — follow it to the actual i32 value it points to, and use that." This "follow the reference to reach the real value" step is what Rust calls dereferencing, and * is the operator that does it. So *n += 1; reads as: "go to the actual number that n points to, and add 1 to it" — which is why, after increment(&mut x) runs, x itself has genuinely changed to 6, even though increment never mentioned x by name.

New concept · Borrowing (&)

Calls the print_scan_result function imported on line 21, passing it &devices rather than plain devices.

The & symbol means borrowing — one of Rust's central ideas. Every value has exactly one "owner" responsible for it; normally, handing a value to a function gives that function ownership of it, and the original variable can no longer be used afterwards. Writing &devices instead lends the function temporary, read-only access to look at the data without taking it away — so devices is still perfectly usable by the rest of main after this line, if it needed to be.

Learn more about borrowing and ownership, in general

There are two kinds of borrow: a shared borrow &T (read-only — any number of these can exist at once) and an exclusive borrow &mut T (read-write — only one may exist, and no shared borrows may exist alongside it). The compiler's "borrow checker" verifies these rules for every piece of code before it's even allowed to run, which is how Rust avoids both data races and dangling references without a garbage collector.

fn print_len(s: &String) { // borrows the String, does not take ownership
    println!("{}", s.len());
}

let text = String::from("hello");
print_len(&text);
println!("{text}"); // still usable here: ownership was never moved away

Without the &, writing print_len(text) would move ownership of text into the function, and the line println!("{text}") afterwards would fail to compile.

It simply becomes impossible to reach from this point onward, because the name bus now points at this new, wrapped value instead. (Rust's official name for reusing a variable name like this, for a brand new and separate variable, is "shadowing" — but the plain idea is just: the old name now points somewhere else.) Learn more about reusing a variable name, in general

Reusing a variable name like this creates a completely new, independent variable — it does not change the previous one in any way, it only makes the previous one impossible to refer to by that name from that point onward. This is different from mut: a mut variable is the exact same variable being changed in place, and it must keep the exact same type the whole time. Reusing a name instead creates a brand new variable every time, and that new variable is even allowed to have a completely different type than the previous one did. This is commonly used to transform a value step by step.

let value = "  42  ";
let value = value.trim();                // still a &str, now trimmed
let value: i32 = value.parse().unwrap(); // now a brand new variable, an i32

If value had instead been declared mut, you would not be able to change it from a &str into an i32 — changing a mut variable in place always keeps the same type; only reusing the name for a new variable can change the type.

New concept · Result & .ok()
Learn more about Result and Option, in general

Result<T, E> is an enum with two variants: Ok(T) (success, carrying a value) or Err(E) (failure, carrying an error). Common ways to handle one: match it explicitly, use the ? operator to pass the error up to the caller, call .unwrap()/.expect() to crash immediately if it's an error, or call .ok() to convert it into an Option<T> and throw the error away. Option<T> is the closely related enum for "a value that might simply be absent": Some(T) or None.

fn parse_age(input: &str) -> Result<u8, std::num::ParseIntError> {
    input.parse::<u8>()
}

match parse_age("30") {
    Ok(age) => println!("Age: {age}"),
    Err(e) => println!("Invalid: {e}"),
}

let maybe_age: Option<u8> = parse_age("oops").ok(); // None, the error is discarded

The key idea both types share: the compiler forces you to at least acknowledge that something might be missing or might have failed — you can't accidentally use a value that was never there.

blink_task::blink_task(led) calls the blink_task function inside the blink_task module (imported on line 22), handing it the led pin from line 45. Because that function is itself async, calling it doesn't run it immediately — it produces a description of a background job waiting to be run.

spawner.spawn(...) takes that job and actually schedules it to start running as an independent background task, using the spawner parameter from line 32. From this point on, the blink task runs concurrently with the rest of main and the other tasks below.

.spawn(...) reports back whether scheduling succeeded, as a Result value — Rust's standard way of representing "either this succeeded, or here is what went wrong", which forces code to at least acknowledge that failure is possible instead of silently ignoring it. .ok() is called on that result to explicitly say "if this failed, discard the error and do nothing about it" — a deliberate, visible choice to ignore the extremely rare failure case (running out of task slots), rather than leaving it unhandled by accident.

Glossary — every concept used in this file

A single place to look up any term from the explanations above.

Crate

A package of Rust code — roughly the same idea as a library. Some crates are written by other people and listed as dependencies (e.g. esp_hal); a project's own code is also organised as one crate.

Module (mod)

A named grouping of related code inside a crate, similar to a folder, used to keep a project organised.

Import (use)

Brings a name into scope so it can be written directly (e.g. Spawner) instead of by its full path (embassy_executor::Spawner) every time.

Variable (let)

A name bound to a value. Immutable (unchangeable) by default; add mut to allow it to change later.

Mutability (mut)

An explicit opt-in that allows a variable's value to be changed after it is created. Without it, a variable can only ever be set once.

Shadowing

Declaring a new variable that reuses an existing name. The old value isn't changed — it simply becomes unreachable, because the name now points at the new value instead.

Function & associated function

A reusable named block of code. An "associated function" belongs to a type and is called with Type::function(), most often used as a constructor (conventionally named new).

Method call

A function called directly on a value using dot syntax, e.g. value.method(). Calls can be chained: value.a().b() means "do a(), then do b() to the result".

Struct & fields

A custom data type that groups several named values together. Individual values inside it are reached with a dot, e.g. peripherals.SYSTEM.

Enum

A type that can only ever be one of a fixed, named set of values, e.g. Level::Low or Level::High.

Generics (<T>)

Angle brackets after a type name showing what it's a container/wrapper for, e.g. StaticCell<Clocks> is "a StaticCell holding a Clocks value".

Lifetime ('static, 'a)

An annotation, always starting with an apostrophe, describing how long a borrowed reference is guaranteed to stay valid. 'static means "for the entire remaining life of the program".

Borrowing (&)

Temporary, read-only (or with &mut, temporary read/write) access to a value without taking ownership of it away from its original variable.

Ownership

Rust's rule that every value has exactly one variable responsible for it at a time. Handing a value to a function normally transfers that responsibility, unless it is borrowed with & instead.

Static variable (static)

A value stored at one fixed memory location for the whole program run, rather than being created and destroyed inside a single function call.

Attribute (#[...] / #![...])

An instruction to the compiler that changes how it treats a piece of code, rather than being part of the program's own logic. The ! form applies to the whole file; the plain form applies only to the next item.

Macro (name!(...))

Code that generates other code at compile time. Always recognisable by a trailing !, e.g. println!(...).

Comment (//, ///)

Text ignored by the compiler, written for human readers. Triple-slash comments specifically document the item on the next line.

async function & task

A function that is allowed to pause itself while waiting for something, letting other work happen on the same processor in the meantime. Passing one to spawner.spawn(...) starts it running as an independent background task.

Mutex

A tool that lets multiple tasks safely take turns accessing the same shared data, one at a time, so it's never read or changed by two tasks simultaneously.

Result & .ok()

Result represents "either this succeeded, or here is what went wrong", forcing failure to be acknowledged rather than ignored by accident. Calling .ok() is an explicit, visible choice to discard a possible error.

String formatting ({})

Empty curly braces inside a text string used with println! act as placeholders, filled in order by the extra values listed after the string.
